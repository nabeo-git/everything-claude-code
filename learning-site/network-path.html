経路とエラー — プロキシ・FW・パケットフィルタの実作業ノウハウ

このページは実作業編(付録)です。 書籍ベースの初級解説ではなく、実務でネットワークのトラブル ——「外部サイトにアクセスできない」「見慣れないエラーが返る」——に出会ったときに、 どの機器が・なぜそのコードを返したのかを切り分けるための手順をまとめています。 HTTPのステータスコードを読んだあとの、現場向けの続編として読んでください。

Webのアクセスは、あなたのブラウザとサーバが直接つながっているとは限りません。 途中にはプロキシ・ファイアウォール・ゲートウェイといった中継装置が並んでいて、 そのどれかが「あなたの代わりに」エラーを返すことがあります。 見えたステータスコードは、目的のサーバではなく途中の機器の判断かもしれません。 このページでは、Squidプロキシの 403 と経路上のファイアウォールの 503 という 実際の例を軸に、機器ごとの挙動の違いと、原因の調べ方を整理します。

このページの内容

  1. 経路にいる機器たち
  2. 機器ごとの「遮断」の挙動の違い
  3. どの機器が返したかを見分ける
  4. 原因の調べ方(具体的な手順)
  5. ケーススタディ: Squid 403 と FW 503

1. 経路にいる機器たち

社内や組織のネットワークから外部サイトへアクセスするとき、通信は次のような機器を順に通ります。 「クライアント → サーバ」の一直線ではなく、途中に何段も関所があるのが実際の姿です。

  1. クライアント ブラウザやアプリ、あるいは curl のようなコマンド。ここからHTTPリクエストが出発する。
  2. フォワードプロキシ(例: Squid) 組織の「外部への出口」。誰がどこへアクセスしてよいかをACL(アクセス制御リスト)で判断し、許可された通信だけを外へ中継する。ログ取得やキャッシュも担う。HTTPを理解して動くアプリケーション層の機器。
  3. ファイアウォール / ルータ パケット(通信の小包)単位で通す・通さないを判断するネットワーク層(L3/L4)の機器。基本はIPアドレスやポート番号を見るだけで、HTTPの中身は見ない。ただし最近の「次世代ファイアウォール」やWAFはアプリケーション層まで見る。
  4. ゲートウェイ / ロードバランサ(サーバ側) 目的のサーバの手前で受け付ける中継役。上流(本当のサーバ)に取り次ぐ。上流に届かなければ、自分でエラーを生成して返す。
  5. オリジンサーバ 本当に応答を作る目的のサーバ。ここまで到達して初めて、そのサーバ自身のステータスコード(200や404など)が返る。

いちばん大事な前提。 上の 2〜4 の機器は、オリジンサーバに代わって独自にHTTP応答を作って返すことができます。 つまり画面に出た 403 や 503 は、目的のサーバが出したとは限らず、 途中の関所が出した「ここから先へは行かせません」の合図かもしれない、ということです。 「誰が返したのか」を意識するのが、切り分けの第一歩です。

2. 機器ごとの「遮断」の挙動の違い

「アクセスを止める」と一口に言っても、機器の種類とその設定によって返ってくるものがまったく違います。 ここが混乱しやすいポイントなので、表で整理します。

機器・動作 何をするか クライアントから見える現象 HTTPコード 速さ
パケットフィルタFW: DROP(破棄) パケットを黙って捨てる。返事を一切しない。 反応が返らず、しばらく待たされる なし(HTTPまで到達しない) 遅い(タイムアウトまで待つ)
パケットフィルタFW: REJECT(拒否) TCPの RST や ICMP到達不能を返して即座に断る。 「接続が拒否されました(Connection refused)」 なし(HTTPまで到達しない) 速い(即座)
フォワードプロキシ(Squid)のACL拒否 プロキシ自身がHTTP応答を生成して返す。 403 Forbidden のエラーページ 403(4xx) 速い(即座)
プロキシ認証が必要 「まず認証してください」と要求する。 プロキシ認証ダイアログ 407(4xx) 速い(即座)
ゲートウェイ/プロキシが上流に届かない 目的サーバへ接続できず、自分でエラーを返す。 不正な応答なら 502、時間切れなら 504 502 / 504(5xx) 502は速い / 504は遅い(タイムアウト)
アプリ層FW / WAF / 機器の意図的ブロック HTTPを解釈する機器が、ブロックの合図として応答を返す。 503 Service Unavailable など 503 / 502(5xx) 速い〜中

純粋なパケットフィルタFWは、HTTPのステータスコードを出しません。 L3/L4の機器はHTTPを話さないので、遮断は「黙って破棄(DROP)」か「RSTで拒否(REJECT)」になり、 画面にはタイムアウトや接続拒否として現れます。 だから「ファイアウォールが 503 を返した」という場合、実際には HTTPを解釈するアプリ層の機器(次世代FW・WAF・プロキシ・ゲートウェイ)が返している、 と考えるのが自然です。「どの層の機器か」を意識すると、見える現象と原因が結びつきます。

4xx と 5xx は「責任の所在」が違います。 HTTPのページでも触れたとおり、 4xx = あなたの依頼を拒否(リクエスト側・ポリシーの問題)、 5xx = サービスを果たせなかった(サーバ側・経路側の問題)です。 Squidの 403 は「この宛先へ出ることをポリシーで拒否」——まさに4xxがふさわしい。 一方 503 は「一時的に応答できない」の意味なので、恒久的なブロックの合図に使うと 本来の意味からは少しズレます(詳細は後述のケーススタディで)。

3. どの機器が返したかを見分ける

エラーに出会ったら、まず「HTTPの応答が返ってきたのか、それともネットワークレベルで止まったのか」を分けます。 これだけで、疑うべき機器の層が絞れます。

  1. そもそもHTTPの応答(3桁のコード)が返ったか? 返ったなら、HTTPを話す機器(プロキシ・ゲートウェイ・アプリ層FW・オリジン)が応答している。次の手順へ。返らない(タイムアウト/接続拒否/リセット)なら、L3/L4のパケットフィルタFWや、ネットワーク到達性そのものを疑う。
  2. コードのクラス(先頭の数字)を見る 4xxならリクエスト側・ポリシー(認可の拒否など)。5xxなら経路側・上流(果たせなかった)。同じ「アクセスできない」でも、この2つは原因の方向が逆。
  3. 応答ヘッダとエラーページで「差出人」を特定する Via / Server / X-Cache / X-Squid-Error といったヘッダや、エラーページの見た目・文言を見る。プロキシやゲートウェイは自分の名前を刻むことが多い。Squidなら Via: 1.1 ... (squid/…) や X-Squid-Error が動かぬ証拠になる。
  4. 遅延の有無から推測する 即座に返る拒否(403 や RST)は「見た瞬間に断った」。待たされた末のタイムアウト(504 や接続タイムアウト)は「届かず時間切れになった」。反応までの時間そのものが手がかりになる。

参考までに、Squidが自分で返す 403 の応答は、ヘッダに指紋がはっきり残ります。

Squidが返す 403(ヘッダに差出人が刻まれる)

HTTP/1.1 403 Forbidden
Server: squid/5.7
Via: 1.1 proxy.example.com (squid/5.7)
X-Squid-Error: ERR_ACCESS_DENIED 0
Content-Type: text/html; charset=utf-8

<html><head><title>ERROR: The requested URL could not be retrieved</title></head>
...(Squidの定型エラーページ)...

一方、経路上の機器がブロックの合図として返す 503 は、たとえばこうです。

ゲートウェイ/アプリ層機器が返す 503

HTTP/1.1 503 Service Unavailable
Server: gateway
Content-Type: text/html; charset=utf-8
Retry-After: 120

<html><body>Service Unavailable</body></html>

4. 原因の調べ方(具体的な手順)

実際に手を動かして切り分けるときの順番です。 上から順に、範囲を狭めていくのがコツです。 (コマンド中のドメインはすべて説明用の例示です。)

  1. まず詳細付きでリクエストしてみる curl -v https://example.com/ で、実際に送られたリクエストと返ってきたレスポンス(ステータス行・全ヘッダ)をそのまま見る。どのプロキシ設定が使われたかも表示される。
  2. プロキシ経由と直結を比べる curl -x http://proxy.example.com:3128 -v https://example.com/ と、プロキシなし(curl --noproxy '*' -v ...)で挙動が変わるか。プロキシ経由のときだけ 403 が出るなら、原因はプロキシのACLで確定に近い。
  3. 応答ヘッダで機器を特定する Via / Server / X-Cache / X-Squid-Error を確認。中継装置は自分の名前を刻みがち。ここで「誰が返したか」がほぼ分かる。
  4. どの段階で止まっているか時間を測る curl -o /dev/null -s -w 'namelookup=%{time_namelookup} connect=%{time_connect} start=%{time_starttransfer} total=%{time_total}\n' https://example.com/。名前解決・接続・応答開始のどこで時間がかかっているかで、DNS・TCP・上流のどこが怪しいか見える。
  5. L3/L4の到達性をHTTPと切り離して確認する nc -vz example.com 443(TCPが張れるか)、traceroute example.com や tcptraceroute example.com 443(どのホップで止まるか)、ping example.com(ICMP)。ここで止まるなら、HTTP以前のパケットフィルタFWやルーティングの問題。
  6. DNSを別問題として除外する dig example.com / nslookup example.com。名前解決の失敗を「アクセス禁止」と取り違えないように切り分ける。
  7. TLS層を切り分ける openssl s_client -connect example.com:443 -servername example.com。証明書やTLSハンドシェイクの失敗は、HTTP以前の別レイヤの問題として扱う。
  8. 機器側のログで裏を取る Squidの access.log に TCP_DENIED/403 があれば、ACL拒否の確定的な証拠。ファイアウォールやゲートウェイのログでも、該当時刻のブロック記録を確認する。クライアント側の推測を、機器側のログで確定させるのが締めくくり。

切り分けの背骨は「レイヤを1つずつ潰す」こと。 DNS(名前解決)→ TCP(到達性)→ TLS(暗号化)→ HTTP(アプリケーション)と、 下の層から順に「ここは正常」と確認していけば、問題がどの層・どの機器にあるかが必ず絞れます。 エラーコードだけを睨むより、この順で潰すほうが速く確実です。

5. ケーススタディ: Squid 403 と FW 503

実際の現場で、Squidプロキシが 403、経路上のファイアウォールが 503 を返す、という挙動を観測したとします。 一見バラバラですが、ここまでの枠組みで読み解くと、それぞれが筋の通った動作だと分かります。

Squid の 403 — 標準動作、意味的にも正しい

フォワードプロキシのSquidが、ACLでこの宛先への外部アクセスをポリシー拒否したときの既定の動作。 外部サーバには一切到達せず、Squid自身が代わりに 403 を生成している。 4xx=「あなたの依頼(この宛先へ出たい)を拒否」なので、意味的にもドンピシャ。 access.log には TCP_DENIED/403 が残るはず。

FW の 503 — 意味的には少しルーズ

503=「一時的にサービスを提供できない」。本来「アクセス禁止」を表すのは 4xx なので、 恒久的なポリシーブロックの合図に 503 を使うのは意味的にはズレている。 実際には (a) 経路のゲートウェイが上流に届かず結果的に 503 化した、または (b) アプリ層の機器が詳細を隠す目的で意図的に 503 を返している、のどちらか。

つまり、同じ「外部に出られない」という結果でも、Squidは 4xx(拒否)・FWは 5xx(不能)と別クラスのコードを返しています。 これは矛盾ではなく、それぞれの機器の“立場”の違いがコードに出ているだけです。 Squidは「リクエストをポリシーに照らして拒否した」(=依頼側の問題として 4xx)、 FW側は「サービスを提供できなかった」(=応える側の事情として 5xx)。 どちらの経路をどう通ったか、どの機器が先に応答したかで、見えるコードが変わります。

現場での実感として。 実際にこの2つを目にすると最初は戸惑いますが、落ち着いて 「どのコードが、どの機器から来たのか」を Via やログで一つずつ確かめれば、 403はプロキシのポリシー拒否、503は経路側の事情、ときれいに切り分けられます。 「エラーコードは目的サーバからのものとは限らない。途中の関所が出した合図かもしれない」 ——この一点を思い出せるかどうかが、現場での早さを分けます。

あなたの仮説への答え。 「本来の意味的に、不正アクセスのときに出すべきコードを出しているのか?」—— Squidの 403 は合っています(4xxが拒否の正しいコード)。 FWの 503 は厳密には少しズレています。「禁止」を表す本来のコードは 4xx であって、 5xxは「サーバ側が果たせなかった」を表すため。503が出るのは 「上流に届かなかった副作用」か「意図的だが意味的にはルーズなブロック表現」のどちらか、というのが正確な理解です。
