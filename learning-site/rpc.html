RPC・SOAP・XML-RPC — HTTPを「トンネル」として使う技術

RESTのページでは、URIでリソースに名前を付け、GET・POST・PUT・DELETEを使い分ける設計を学びました。 ところが世の中には、HTTPのPOSTだけを「運び屋」として使い、その中に独自の命令をくるんで送るという、 まったく別の発想の技術があります。その代表がXML-RPCとSOAPです。 これらは歴史的にRESTと同じ2000年前後に登場し、一時はWeb APIの主役でした。 このページでは、これらが「どういうプロトコルで」「どう生まれ」「今どう使われ」「内部でどう動くのか」を、 HTTPの知識の延長として体系的に整理します。そして最後に、初級者がよく疑問に思う 「HTTPのPOSTを使い倒すのは、本来の原則からすると誤用なのか?」という論点に、RESTの視点から答えます。

RPCという発想 — 「遠くの関数を呼ぶ」

まず土台となるRPC(Remote Procedure Call、遠隔手続き呼び出し)という考え方から始めます。 プログラムでは、自分の書いた関数を getUser(123) のように呼び出しますね。 RPCとは、この関数呼び出しをネットワークの向こう側にある別のコンピュータで実行する仕組みです。 手元で getUser(123) と書くと、裏側でその「命令名(getUser)」と「引数(123)」がネットワークを渡り、 遠くのサーバで処理され、結果が返ってくる——あたかもローカルの関数のように、と見せかけるのが狙いです。

RPCは「遠くの家電を操作するリモコン」のようなものです。 ボタン(関数)を押すと、離れた場所にある機械が動く。利用者は電波(ネットワーク)のことを意識せず、 手元のリモコンを操作する感覚のまま遠隔の処理を呼び出せます。 この「距離を感じさせない」ことがRPCの理想です。

ここでRESTとの根本的な違いが見えてきます。両者は「何を中心に考えるか」が正反対です。

観点REST(リソース指向)RPC(手続き指向)
中心に置くもの 名詞(リソース=モノ) 動詞(手続き=動作)
考え方 「ユーザ123というモノを GET する」 「getUser という動作を 123 を引数に呼ぶ」
URIの役割 操作対象(リソース)を指す住所
/users/123		 命令の受付窓口。1つで十分
/api や /RPC2
「何をするか」の決め方 URI + HTTPメソッド ボディに書いた命令名

RPCという発想自体は、Webよりずっと古く1980年代からあります(Sun RPC、後のCORBAやDCOMなど)。 ただし当時のRPCは独自のネットワークの通り道(専用ポート)を使っており、 会社のファイアウォールに阻まれて外部とつながりにくい弱点がありました。 そこで「どこの環境でもたいてい通れるHTTP(ポート80/443)に相乗りしよう」と考えて生まれたのが、 これから見るXML-RPCとSOAPです。この「HTTPに相乗り」という発想が、後の論点すべての出発点になります。

XML-RPC — 最小のHTTP-RPC

XML-RPCは1998年に登場した、非常にシンプルなRPCの仕様です。 名前のとおり「XMLで命令を書き、RPC(遠隔手続き呼び出し)を行う」もので、 やることはたった一つ——「呼びたい命令名」と「引数」をXMLで表現し、HTTPのPOSTで送るだけです。

仕組み

  • リクエストは <methodCall> 要素に、<methodName>(命令名)と <params>(引数)を書く
  • レスポンスは <methodResponse> 要素で返す
  • 送り先のURI(エンドポイント)はいつも1つ。何を呼ぶかはURIではなくボディの中の命令名で決まる

実際に「ID 123 のユーザ情報を取得する(getUser)」を呼ぶと、ネットワークにはこんなメッセージが流れます。

リクエスト(クライアント → サーバ)

POST /RPC2 HTTP/1.1
Host: api.example.com
Content-Type: text/xml
Content-Length: 168

<?xml version="1.0"?>
<methodCall>
  <methodName>getUser</methodName>
  <params>
    <param>
      <value><int>123</int></value>
    </param>
  </params>
</methodCall>

レスポンス(サーバ → クライアント)

HTTP/1.1 200 OK
Content-Type: text/xml
Content-Length: 241

<?xml version="1.0"?>
<methodResponse>
  <params><param><value><struct>
    <member>
      <name>id</name>
      <value><int>123</int></value>
    </member>
    <member>
      <name>name</name>
      <value><string>佐藤花子</string></value>
    </member>
  </struct></value></param></params>
</methodResponse>

注目してほしいのは、URIが /RPC2 という1つだけで、 リクエストラインが常に POST /RPC2 になっている点です。 HTTPのページで学んだ「GETで取得、DELETEで削除」といったメソッドの使い分けは一切ありません。 「何をするか」はすべて、ボディの <methodName> に書かれています。

エラーが起きたときも、XML-RPCは独特です。命令が失敗しても、HTTPのステータスは 200 OK のままで、 失敗の中身はボディの <fault>(フォールト=障害)要素で伝えます。

エラー時のレスポンス(HTTPは200のまま、中身で失敗を伝える)

HTTP/1.1 200 OK
Content-Type: text/xml

<?xml version="1.0"?>
<methodResponse>
  <fault><value><struct>
    <member>
      <name>faultCode</name>
      <value><int>404</int></value>
    </member>
    <member>
      <name>faultString</name>
      <value><string>ユーザが見つかりません</string></value>
    </member>
  </struct></value></fault>
</methodResponse>

ここがXML-RPC(そして次のSOAP)を理解する核心です。 「見つからなかった」という結果を、HTTPの 404 ではなく、ボディの中の faultCode で伝えている—— つまりHTTPは中身を運ぶだけの通り道で、成功も失敗もHTTPの外側(ボディ)で判断しています。 これはRESTの成熟度モデルでいう「レベル0」、 「HTTPをただの通り道として使う」状態そのものです。良い悪いは後のセクションで検討します。

SOAP — エンタープライズ向けのRPC/メッセージング

SOAPは、XML-RPCとほぼ同時期(1998〜2000年)に、Microsoftなどが中心となって作った より本格的なXMLメッセージング仕様です。当初は「Simple Object Access Protocol(シンプルなオブジェクトアクセスプロトコル)」の 略でしたが、実態はまったくシンプルではなくなったため、バージョン1.2からは「SOAP」という略さない固有名詞になりました。 XML-RPCが「最小限」なら、SOAPは「企業システムの厳しい要求(セキュリティ・信頼性・契約)にすべて応える重装備」です。

仕組み — Envelope(封筒)構造

SOAPメッセージは、手紙を封筒に入れるように、必ず Envelope(封筒)で全体を包みます。

Envelope soap:Envelope(封筒。全体を包む一番外側) この中に Header と Body が入る。
Header(任意) soap:Header(添え状=メタデータ) 認証情報、トランザクションID、署名など「本文以外の付帯情報」を入れる。WS-Security等の拡張はここを使う。
Body(必須) soap:Body(本文=呼び出したい処理そのもの) 呼びたい操作と引数、または結果。失敗時はここに soap:Fault(障害情報)が入る。

「ID 123 のユーザを取得する」をSOAPで呼ぶと、こうなります。XML-RPCより格段に情報量が多いことに注目してください。

リクエスト(クライアント → サーバ)

POST /UserService HTTP/1.1
Host: api.example.com
Content-Type: application/soap+xml; charset=utf-8
Content-Length: 420
SOAPAction: "http://example.com/users/GetUser"

<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <auth:Token xmlns:auth="http://example.com/auth">abc123xyz</auth:Token>
  </soap:Header>
  <soap:Body>
    <GetUser xmlns="http://example.com/users">
      <userId>123</userId>
    </GetUser>
  </soap:Body>
</soap:Envelope>

レスポンス(サーバ → クライアント)

HTTP/1.1 200 OK
Content-Type: application/soap+xml; charset=utf-8

<?xml version="1.0"?>
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Body>
    <GetUserResponse xmlns="http://example.com/users">
      <user>
        <id>123</id>
        <name>佐藤花子</name>
      </user>
    </GetUserResponse>
  </soap:Body>
</soap:Envelope>

リクエストに SOAPAction という専用のHTTPヘッダがある点にも注目してください。 本来HTTPヘッダで運ぶべき「何をしたいか」の情報を、SOAPは独自ヘッダとして追加しています。 これも「HTTPの仕組みをそのまま使うのではなく、上に独自の層を重ねる」というSOAPの姿勢の表れです。

エラーは soap:Fault で

失敗時は Body の中に soap:Fault を入れて返します。SOAPの場合、HTTPステータスは 成功なら 200、サーバ側の障害なら 500 を使うのが一般的ですが、 「ユーザが見つからない」といった意味の違いはHTTPの 404 では区別せず、Faultの中身で表現します。

  <soap:Body>
    <soap:Fault>
      <soap:Code><soap:Value>soap:Sender</soap:Value></soap:Code>
      <soap:Reason>
        <soap:Text xml:lang="ja">ユーザが見つかりません</soap:Text>
      </soap:Reason>
    </soap:Fault>
  </soap:Body>

SOAPを取り巻く仕様のエコシステム

SOAPは単体では終わらず、企業システムの要求に応える多数の関連仕様(通称 WS-*、ダブリューエス・スター)を伴います。

仕様役割
WSDL(ウィズドル) そのサービスが「どんな操作を・どんな引数で・どんな戻り値で」提供するかを機械可読なXMLで定義した仕様書。これを読めばクライアント側のコードを自動生成できる。
WS-Security メッセージ単位の暗号化・電子署名・認証。通信路だけでなくメッセージそのものを守る。
WS-ReliableMessaging 「確実に1回だけ届ける」など配送の信頼性保証。
UDDI SOAPサービスを登録・検索するための電話帳のような仕組み(現在はほぼ使われない)。

SOAPは建前上トランスポート(通り道)に依存しない設計で、HTTPだけでなくメール(SMTP)などでも運べることになっています。 だからこそHTTPのステータスコードに意味を持たせず、成功/失敗を自前のFaultで表現します。 「どの通り道でも同じように動く」ことを優先した結果、HTTP固有の便利機能をあえて使わない——これがSOAPの一貫した思想です。 ただし現実には、SOAPメッセージの99%はHTTPで運ばれています。

仕組みの共通点 — HTTPを「トンネル」にする

XML-RPCもSOAPも、やっていることの本質は同じです。HTTPのPOSTという封筒の中に、 自分たちのメッセージ(XML)を丸ごと入れて運ぶ。HTTPはその中身を一切解釈せず、ただ運ぶだけ。 このように、あるプロトコルを別のプロトコルの中に包んで通すことをトンネリング(tunneling)と呼びます。 SOAP/XML-RPCは「HTTPトンネリング」でRPCを実現しているわけです。

宅配便(HTTP)の段ボール箱に、さらに自社専用の箱(SOAP/XML-RPCメッセージ)を入れて送るイメージです。 宅配業者(HTTP)は外側の箱だけ見て運びます。中の専用箱の開け方や中身のルールは、 送り主と受取人だけが知っている独自の取り決め。宅配便の「速達」「着払い」といった便利機能(HTTPのメソッドやステータス)は、 中の専用箱には関係なく使われません。

3つの技術がHTTPをどう使うかを並べると、違いが一目で分かります。

観点 REST(レベル2) XML-RPC SOAP
使うHTTPメソッド GET/POST/PUT/DELETE を使い分け POST のみ POST のみ
URI(エンドポイント)の数 リソースごとに多数 原則1つ 原則1つ(サービス単位)
「何をするか」の指定場所 URI + メソッド ボディの methodName ボディの要素名 + SOAPAction ヘッダ
成功/失敗の伝え方 HTTPステータス(200/404/400…) 常に200。失敗はボディの fault 200/500 中心。詳細はボディの Fault
データ形式 主にJSON XML(簡素) XML(Envelope構造)
Content-Type application/json text/xml application/soap+xml
GETのキャッシュ 効く(条件付きGET等) 効かない(全部POST) 効かない(全部POST)
仕様の重さ 軽い(ゆるやかな規約) 非常に軽い 重い(WSDL・WS-* 群)

「HTTP POSTの誤用」なのか? — RESTの視点から

ここまで見ると、素朴な疑問がわきます。 「取得するだけの処理まで全部POSTにして、URIも1つしか使わないのは、HTTPの使い方として間違っているのでは?」。 これはWebの技術を学ぶ人が必ずぶつかる良い問いです。結論を急がず、両方の言い分を見てみましょう。

「誤用だ」と言われる理由(RESTの立場)

RESTは、HTTPを単なる通り道ではなく「アプリケーションプロトコル」—— それ自体が意味を持つ言語として最大限に活用します。その立場から見ると、SOAP/XML-RPCは HTTPが用意した便利な仕組みをことごとく使い捨てにしています。

もったいない点何が失われるか
取得もすべてPOST(安全なメソッドを使わない) 「読むだけ」だと機械に伝わらず、キャッシュが効かない。同じ問い合わせでも毎回サーバに届き、負荷が減らない。
URIが操作対象を指さない(1つのエンドポイント) 個々のデータにURIで名前が付かないので、ブックマークもリンクも共有もできない。クールURIやハイパーメディアの利点が消える。
HTTPステータスコードを使わない(全部200) 途中のプロキシ・CDN・監視ツールが「成功か失敗か」を判断できない。エラーの中身を毎回ボディまで開けないと分からない。
統一インターフェースに反する 「限られた作法で誰とでも話せる」というWebの強みが使えず、サービスごとに独自の呼び出し規約を覚える必要がある。

「誤用ではない/合理的だった」という反論

  • 仕様違反ではない。 POSTは元々「その他の処理」を広く許容するメソッドで、「命令をボディで送る」使い方はHTTPの規約に反していません。HTTPは元来アプリ間でデータを転送する汎用プロトコルでもあります。
  • 現実的な大勝利だった。 当時、企業のファイアウォールは外向きのHTTP(ポート80/443)しか通さないのが普通でした。従来のRPC(CORBA/DCOM)は専用ポートが塞がれて社外と通信できない。「誰でも通れるHTTPに相乗りする」ことで、初めて企業間・インターネット越しのRPCが実用になった——これは実務上とても大きな価値でした。
  • 思想として一貫している。 SOAPは「どの通り道でも同じに動く」ことを重視したので、HTTP固有のステータスコードにあえて依存しないのは、その設計方針からすると筋が通っています。

だから正確には、「誤用」というよりHTTPというものの捉え方の違いです。
・RESTは、HTTPを「意味を持つアプリケーションプロトコル」とみなし、メソッド・ステータス・URIを言葉として使い倒す。
・SOAP/XML-RPCは、HTTPを「中身を問わず運んでくれるトランスポート(トンネル)」とみなし、意味づけは自分たちの層で行う。
同じ POST でも、狙いがまるで違うのです。書籍『Webを支える技術』が繰り返し問いかけるのも、この 「HTTPをどう捉えるか」というテーマにほかなりません。そして歴史は、シンプルにHTTPを活用するRESTの側に軍配を上げました(次のセクション)。

成り立ちと勢力図の変遷

SOAP/XML-RPCとRESTは、実はほぼ同時に生まれた「双子のライバル」でした。その勝敗が決まるまでを年表で追います。

時期出来事意味
1998年 XML-RPC 公開 「XMLをHTTP POSTで送るだけ」の最小RPCが登場。手軽さで一部に普及。
1998〜2000年 SOAP 登場(Microsoft/IBM など) XML-RPCを企業向けに拡張。大手ベンダが揃って推進し、Web APIの「本命」と目される。
2000年 Roy Fielding が REST を提唱 「Webの成功はシンプルな仕組みにある」と理論化(→ REST)。当時はSOAPほど注目されず。
2000年代前半 SOAP / WS-* の隆盛 .NET や Java EE が全面支援。エンタープライズのシステム間連携の標準として広く採用される。ただしWS-*が増え続け、複雑さが深刻化。
2005年ごろ Web 2.0 とシンプルなAPIの流行 大手のWebサービスが、扱いやすいREST + JSONのAPIを公開し始める。開発者が「SOAPは重すぎる」と実感。
2008〜2010年ごろ REST + JSON が公開Web APIの主流に Ajaxやスマホアプリとの相性の良さ(ブラウザからそのまま扱える)も後押し。『Webを支える技術』刊行(2010)はこの転換点。
2010年代〜現在 新規開発でのSOAP採用は激減 公開APIはREST、社内の高速通信は後発のgRPCへ。SOAPは既存の基幹系で維持される「レガシー」寄りの位置に。

なぜSOAPは主役の座を譲ったのか。ひとことで言えば「複雑さに見合わなくなった」からです。 WSDLを書き、WS-*を積み上げ、専用ツールでコード生成し……という重厚な手順は、 厳格さが必要な企業間取引には向いていましたが、「ブラウザのJavaScriptからサッと呼びたい」 「スマホアプリで手軽に使いたい」というAjax以降のニーズには重すぎました。 そこへ、HTTPをそのまま活かしJSONで軽く返すRESTが、ちょうど良い落としどころとして広まったのです。

現在の使われ方 — 今どこで動いているか

「もう使われていない古い技術」と切り捨てるのは正確ではありません。2026年現在の実像はこうです。

SOAP — 今も現役(特定分野)

金融・決済、通信キャリア、行政・公共、企業間(B2B)の基幹システムで根強く稼働。厳密なセキュリティ(WS-Security)や、 WSDLによる「契約」を重視する世界で選ばれ続けている。既存資産が巨大なため、置き換えより維持が現実的。

XML-RPC — ほぼ歴史的

新規採用はまれ。ブログソフトのWordPressに残る xmlrpc.php などに名残がある程度。 仕組みがシンプルゆえに攻撃の入り口にもなりやすく、セキュリティ上あえて無効化されることも多い。

RPCの発想 — 形を変えて継承

「遠くの関数を呼ぶ」という発想自体は健在。現代版はgRPC(HTTP/2上のバイナリRPC。社内マイクロサービス間の高速通信)や JSON-RPC(XML-RPCのJSON版)。SOAP/XML-RPCの子孫と言える。

公開Web API — REST + JSON が共通語

不特定多数に開くAPIは、依然としてRESTスタイル + JSONが事実上の標準(→ API設計のページ)。 HTTPをそのまま活かせる手軽さが、今も選ばれる最大の理由。

XML-RPCとセキュリティ。 XML-RPCのエンドポイントは「1つのURIに何でもPOSTできる」性質上、 総当たり攻撃や大量リクエストの標的になりやすいことが知られています。 使っていないのに有効化されたままだと危険なので、不要なら無効化するのが定石です。 「シンプルさ」は利点であると同時に、攻撃者にとってのシンプルさでもある、という教訓です。

2026年の実務での選び方(目安)。 新しくAPIを作るなら——外部公開・ブラウザやアプリから使う → REST + JSON。 社内のサービス間で高速・大量にやりとりする → gRPC。 金融・行政など既存のSOAP資産と連携する必要がある → SOAPを維持。 新規でXML-RPCやSOAPをゼロから選ぶ理由は、特殊な事情がない限りほぼありません。 とはいえ、既存システムの改修や他社との連携でSOAPに出会う可能性は今も十分あります。 「なぜこう作られているのか」を本ページの視点で読み解ければ、恐れることはありません。
