HTTP — Webの配送プロトコル

HTTP(HyperText Transfer Protocol)は、URIで示された住所とデータをやりとりするための 通信の手順(プロトコル)で、Webの三本柱のうち「転送」を担当します。 ブラウザの閲覧も、スマホアプリの通信も、Web APIの呼び出しも、すべてこのHTTPの上で動いています。 このページはサイトの中核です。生のHTTPメッセージをたくさん読みながら、 メソッド・ステータスコード・ヘッダ・ステートレス性という4つの柱を身につけましょう。 書籍『Webを支える技術』第3部「HTTP」に対応する内容です。

HTTPはどこにいるのか

まず位置の確認です。インターネットの通信はTCP/IPという階層構造で整理されており、 HTTPはそのいちばん上のアプリケーション層にいます。 下の層ほど「土台」に近く、上の層ほど「アプリの都合」に近くなります。

アプリケーション層 HTTP 「このURIのリソースをください/保存してください」というアプリケーションの会話。メールのSMTPやDNSも同じ層の仲間。
トランスポート層 TCP データを欠け・重複・順序の乱れなく相手のプログラムまで確実に届ける。ポート番号で窓口を区別する。
インターネット層 IP IPアドレスを頼りに、パケット(データの小包)を世界中のネットワーク越しに宛先のコンピュータまで運ぶ。
ネットワークインターフェース層 イーサネット / Wi-Fi など ケーブルや電波で、隣接する機器まで物理的に信号を届ける。

つまりHTTPは、TCP/IPという配送インフラの上に乗ったアプリケーション層のプロトコルです。 HTTP自身は「確実に届ける」仕事を下の層に任せ、 「何を依頼し、どう応答するか」という会話のルールに専念しています。 この割り切りのおかげで、HTTPの仕様はシンプルに保たれています。

下の層の詳細(IPアドレスの割り当てやTCPの再送制御など)はネットワークの専門書の領域なので、 本サイトでは深入りしません。「HTTPは土台の上の会話ルール」という位置づけだけつかめば十分です。

リクエストとレスポンス

Webとはのページで見たとおり、HTTPの通信は必ず クライアントがリクエスト(依頼)を送り、サーバがレスポンス(応答)を返すという1往復で行われます。 やりとりされるメッセージは、実はただのテキストで、構造も決まっています。

リクエストメッセージ

① リクエストライン(メソッド + パス + バージョン)
② ヘッダ(付加情報。複数行)
③ 空行(区切り)
④ ボディ(送るデータ本体。無いことも多い)

レスポンスメッセージ

① ステータスライン(バージョン + コード + 説明句)
② ヘッダ(付加情報。複数行)
③ 空行(区切り)
④ ボディ(返すデータ本体。HTMLやJSONなど)

実例① GET — リソースを取得する

リクエスト(クライアント → サーバ)

GET /users/123 HTTP/1.1
Host: www.example.com
Accept: text/html
User-Agent: Mozilla/5.0 ...

レスポンス(サーバ → クライアント)

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 87

<!DOCTYPE html>
<html lang="ja">
<body><h1>佐藤花子</h1></body>
</html>

リクエストの1行目「GET /users/123 HTTP/1.1」がリクエストラインです。 「GETという方法で、/users/123 というリソースを、HTTP/1.1の作法でください」と読みます。 レスポンスの1行目「HTTP/1.1 200 OK」がステータスラインで、「成功しました」という結果報告です。

実例② POST — データを送信する(フォーム送信)

ログインフォームや検索フォームの「送信ボタン」を押すと、こんなリクエストが飛びます。

リクエスト(フォームの内容をボディに載せて送る)

POST /search HTTP/1.1
Host: www.example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 28

q=%E5%AF%BF%E5%8F%B8&lang=ja

レスポンス(検索結果のページ)

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html lang="ja">
<body><h1>「寿司」の検索結果</h1>...</body>
</html>

GETと違い、POSTでは空行の下にボディがあります。 application/x-www-form-urlencoded は「フォームの入力値を 名前=値&名前=値 の形式で送ります」という宣言で、 値の日本語は%エンコーディングされています(%E5%AF%BF%E5%8F%B8 = 寿司)。

HTTPメッセージは人間が読めるただのテキストです。 そして構造は「1行目(何をしたいか/どうなったか)+ ヘッダ(付加情報)+ 空行 + ボディ(データ本体)」——これだけです。 この単純さこそが、あらゆる言語・あらゆる機器がHTTPを実装できた理由です。 以降の節はすべて、この構造のどこかの部品(メソッド、ステータスコード、ヘッダ)の話にすぎません。

HTTPメソッド

リクエストラインの先頭に書くメソッドは、「リソースをどうしたいか」を表す動詞です。 種類は驚くほど少なく、主要なものは次の7つだけです。

メソッド役割例
GETリソースの取得ページを見る、APIでデータを読む
POST子リソースの作成、データの追加、その他の処理新規投稿、フォーム送信、注文の確定
PUTリソースの更新(丸ごと置き換え)、作成プロフィール全体を新しい内容で置き換える
DELETEリソースの削除投稿を削除する
PATCHリソースの部分的な更新プロフィールのうちメールアドレスだけ変える
HEADヘッダのみ取得(ボディなしのGET)ファイルの更新日時やサイズだけ確認する
OPTIONSそのリソースが受け付けるメソッドの問い合わせAPIが対応する操作の確認(CORSでも利用)

メソッドは宅配便の「伝票の種別」です。「お届け(POST)」「集荷(GET)」「差し替え(PUT)」「回収(DELETE)」—— 種別が数種類に統一されているから、配送網のどの拠点(サーバやプログラム)でも同じように処理できます。 書籍はこれを「統一インターフェース」と呼び、Webの成功の鍵として強調しています。→ RESTのページ

安全性と冪等性 — メソッドの「性格」

書籍第3部の重要トピックが、メソッドの2つの性質です。

  • 安全性(safe) — 実行してもリソースの状態を変化させないこと。安全なメソッドは何回呼んでも、誰が呼んでも、サーバ上のデータは変わりません。
  • 冪等性(べきとうせい、idempotence) — 何回実行しても結果が同じであること。1回実行しても100回実行しても、サーバは同じ状態に落ち着きます。
メソッド安全冪等理由
GET / HEAD / OPTIONS○○読むだけなので状態を変えない。変えないので何回でも同じ。
PUT×○状態は変えるが、「この内容にする」という指定なので、2回実行しても同じ内容になるだけ。
DELETE×○2回削除しても「無い」という同じ状態に落ち着く。
POST××2回実行すると投稿や注文が2件できてしまう。
PATCH××(保証なし)差分の与え方によっては繰り返すたびに結果が変わりうる。

この性質は実務に直結します。通信が途中で失敗したとき、冪等なメソッドは安心して再送(リトライ)できますが、 POSTの再送は二重注文の危険があるため慎重な設計が必要です。 「注文ボタンを2回押さないでください」という画面表示の裏には、この冪等性の問題があるのです。

GETとPOSTの使い分け(初級者向けの目安)

  • 見るだけ・検索するだけ → GET。URIに条件が入るのでブックマークや共有ができ、キャッシュも効きます。
  • データを作る・変える・送る → POST(APIでは更新にPUT/PATCH、削除にDELETEも)。パスワードなどをURIに残さない意味でもPOSTを使います。

「GETなら安全」はサーバ側が守るべき約束でもあります。 GETで届いたリクエストで削除などの副作用を起こす設計は厳禁です。 検索エンジンのクローラ(リンクを機械的にたどるプログラム)がGETでアクセスしただけで データが消える——という事故が実際に起きています。

逆に、取得も含めてほぼすべてをPOSTで処理し、URIを1つしか使わないという設計の技術もあります。 SOAPやXML-RPCがその代表で、HTTPを「中身を問わず運ぶだけの通り道」として使います。 これがHTTP本来の使い方からすると「誤用」なのかどうかも含めて、 別ページ(→ RPC・SOAP・XML-RPCのページ)で体系的に扱います。

ステータスコード

レスポンスの1行目に入る3桁の数字がステータスコードで、処理の結果を表します。 まず覚えるべきは先頭の数字による5分類です。先頭さえ見れば、知らないコードでも大意がつかめます。

分類意味ざっくり言うと
1xx処理中(情報)「受け付けました、続けてください」。日常ではほぼ見ない。
2xx成功「できました」
3xxリダイレクト「別の場所を見てください」
4xxクライアントエラー「あなたの依頼がおかしいです」(リクエストを直せば解決)
5xxサーバエラー「こちらの失敗です」(サーバ側が直るのを待つ)

代表的なコード

コード名前意味と使いどころ
200OK成功。ボディに結果が入る。
201Createdリソースの作成に成功。POSTやPUTへの応答。新しいリソースのURIをLocationヘッダで返す。
204No Content成功したが返すボディがない。DELETEへの応答などで使う。
301Moved Permanently恒久的な移転。URIを変更したときの正しい案内方法。
302Found一時的な移動。ログイン後のページ振り分けなど。
304Not Modified「前回から変わっていない」。キャッシュと組で使う(後述)。
400Bad Requestリクエストの形式が不正。パラメータ間違いなど。
401Unauthorized認証が必要(名乗っていない/認証に失敗)。
403Forbidden認可の拒否(権限・ポリシーで禁止)。認証し直しても解決しない点が401と違う。プロキシがACLで通信を拒否するときの応答もこれ(→ 経路とエラー)。
404Not Foundリソースが存在しない。いちばん有名なコード。
500Internal Server Errorサーバ内部の異常。プログラムのバグなど。
503Service Unavailable一時的に応答不能。メンテナンス中やアクセス集中。

301リダイレクトの往復を見る

URIが引っ越したときの実際のやりとりです。ブラウザはこれを自動でやってくれるので、利用者は移転に気づきません。

① 古いURIへのリクエスト

GET /old-blog/hello HTTP/1.1
Host: www.example.com

② 「恒久的に移転しました」— 新しいURIをLocationヘッダで案内

HTTP/1.1 301 Moved Permanently
Location: https://www.example.com/blog/hello
Content-Length: 0

③ クライアントは案内されたURIへ自動で再リクエスト

GET /blog/hello HTTP/1.1
Host: www.example.com

④ 今度こそ本体が返る

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
...

ステータスコードはプログラムが機械的に分岐できるように数字になっています。 Web APIの設計では「成功したのに200でエラーメッセージを返す」ような使い方は嫌われます。 → API設計のページ

そのエラー、誰が返している? — 経路上の中継装置と4xx/5xx

ステータスコードを読むとき、見落としがちな前提があります。 HTTP応答は、目的のサーバ(オリジン)だけが返すとは限らないということです。 通信の途中にはプロキシ・ゲートウェイ・キャッシュ・ファイアウォールといった中継装置が並んでいて、 そのどれかがオリジンの代わりにエラーを生成して返すことがあります。 つまり、画面に出たコードは「目的のサーバの返事」ではなく「途中の関所の判断」かもしれません。

このとき、さきほどの4xxと5xxの違いが「どちらの立場のエラーか」を読む手がかりになります。 4xx は「あなたの依頼を拒否」(リクエスト側・ポリシーの問題)、 5xx は「サービスを果たせなかった」(サーバ側・経路側の問題)です。

実例:社内プロキシとファイアウォールが別のコードを返す。 組織のネットワークで外部サイトへアクセスしたとき、 出口のプロキシ(Squid)がポリシーで拒否すると、Squid自身が 403 Forbidden を返します (4xx=「この宛先へ出る依頼を拒否」なので意味的にも正しい)。 一方、経路上のファイアウォールがブロックの合図として 503 Service Unavailable を返すこともあります (5xx=「サービスを提供できない」で、恒久的な禁止の合図に使うと本来の意味からは少しズレる)。 同じ「アクセスできない」でも、機器によって返すコードのクラスが違うのです。

どの機器が・なぜそのコードを返したのかを見分け、原因を切り分ける具体的な手順は、 実作業編として別ページにまとめました。パケットフィルタ(DROP/REJECT)の挙動の違いや、 curl -v・Viaヘッダ・ログでの調べ方まで扱います。 → 経路とエラー — プロキシ・FW・パケットフィルタの実作業ノウハウ

HTTPヘッダ

ヘッダは、メッセージのメタデータ(データについてのデータ)です。 宅配便でいえば、荷物の中身そのもの(ボディ)に対する伝票の付加情報—— 「品名: 書籍」「重さ: 500g」「割れ物注意」——にあたります。 「名前: 値」という形式で、1行に1つずつ並びます。よく登場するものを押さえましょう。

ヘッダ方向役割
Hostリクエスト宛先のサーバ名。1台のサーバが複数のサイトを担当できるのはこのヘッダのおかげ。HTTP/1.1で唯一の必須ヘッダ。
Content-Type両方ボディの種類をメディアタイプ(MIMEタイプとも呼ぶ)で示す。これは「大分類/小分類」形式のデータ形式ラベルで、text/html(HTML)、application/json(JSON)、image/png(PNG画像)など。受け取った側はこれを見て解釈方法を決める。
Content-Length両方ボディのサイズ(バイト数)。どこまで読めばメッセージの終わりかを知らせる。
Content-Dispositionレスポンスボディを画面に表示(inline)するか、ファイルとしてダウンロード(attachment)させるかを指示する。保存時のファイル名も指定できる(後述)。
Acceptリクエスト「私はこの形式が受け取れます」という希望(text/html、application/json など)。サーバが表現を出し分ける手がかり。
User-Agentリクエストクライアントの自己紹介(ブラウザ名やアプリ名)。
Cache-Control両方キャッシュ(再利用)の可否や有効期間の指示(後述)。
Set-Cookie / Cookieレスポンス / リクエストサーバがクライアントに小さなメモ(Cookie)を渡し(Set-Cookie)、クライアントが以後のリクエストで毎回提示する(Cookie)。ログイン状態の維持に使う(後述)。
Authorizationリクエスト認証情報(パスワードやトークンなど「本人であることの証明」)を運ぶ。Web APIでは Bearer トークン方式が主流。
Locationレスポンスリダイレクト先や、新規作成されたリソースのURI。

ヘッダは自作もできます(慣習として X- で始めることが多い)。 HTTPが「メソッド+ステータスコード+ヘッダ」という骨組みを固定しつつ、 ヘッダで拡張の余地を残していることが、30年以上使われ続けている柔軟さの源です。

Content-Disposition — ファイルとして保存させる・名前を付ける

Content-Disposition は、「このレスポンスの中身を、ブラウザでどう扱ってほしいか」をサーバが指示するレスポンスヘッダです。値は主に2種類です。

inline(既定)

その場で表示してほしい。PDFや画像をブラウザ内で開くのはこれ。指定がなければ基本この扱い。

attachment

ファイルとして保存(ダウンロード)してほしい。ブラウザは表示せず保存ダイアログを出す。filename で保存名も指定できる。

レスポンス例 — CSVをダウンロードさせ、保存名を指定する

HTTP/1.1 200 OK
Content-Type: text/csv; charset=utf-8
Content-Disposition: attachment; filename="report.csv"

id,name,joined
123,Sato,2024-04-01

何のために使うのか。利用目的は主に次のとおりで、実際のWebサービスで今も広く使われています。

  • ブラウザに表示させず保存させたいとき(CSV・ZIP・請求書PDF・生成した帳票など)。attachment を付けないと、ブラウザが中身を開こうとしてしまう。
  • URLと違う分かりやすい名前で保存させたいとき。ダウンロード用URLが /reports/9f3c-download のような機械的な文字列でも、保存名を 2026年度_請求書.pdf にできる。
  • 動的に生成したファイル(その場で作ったCSVやPDF)に、意味のある名前を付けて渡したいとき。

日本語ファイル名が「バグる」理由と正しい書き方。 古い形式の filename="報告書.pdf" のように日本語をそのまま書くと文字化けすることがあります。 これは filename パラメータが本来ASCII(英数字)しか正しく扱えないためで、 ブラウザごとに解釈が違って文字化け(mojibake)が起きます。 正しくは、RFC 6266 / RFC 5987 で定められた filename*(アスタリスク付き)を使い、 文字コードを明示して%エンコーディングした値を渡します。

日本語ファイル名の正しい指定 — filename* を使い、UTF-8で%エンコーディング

HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment;
  filename="report.pdf";
  filename*=UTF-8''%E5%A0%B1%E5%91%8A%E6%9B%B8.pdf

filename*=UTF-8''… の「UTF-8''」は文字コードの宣言で、続く %E5%A0%B1… は 「報告書.pdf」をUTF-8で%エンコーディングしたものです。 古いブラウザ用に filename="report.pdf"(ASCIIの予備)も併記し、対応ブラウザには filename* を使わせるのが定石です。 現在の主要ブラウザは filename* に対応しているので、この書き方なら日本語ファイル名も文字化けせず保存できます。

ステートレス性

HTTPの設計上の大きな特徴がステートレス(stateless)であることです。 ステートレスとは、サーバがクライアントの「前回までのやりとり」(アプリケーション状態)を覚えないという方針のこと。 サーバにとって、すべてのリクエストは「初対面の依頼」として処理されます。

書籍の有名なたとえがハンバーガーショップの注文です。 状態を覚える(ステートフルな)店なら「ハンバーガーください」「セットで」「ポテトはLで」と会話を積み重ねられます。 しかしステートレスな店では、店員は直前の会話を覚えていないので「セットで」だけでは通じません。 毎回「ハンバーガーセットをポテトLで1つください」と、 必要な情報をすべて含んだ完全な注文を言う必要があります。 HTTPのリクエストはこの「完全な注文」方式です(こうしたメッセージを自己記述的メッセージと呼びます)。

内容
利点サーバはリクエストを処理したら忘れてよいので、サーバを何台にも増やして負荷を分散しやすい(スケーラビリティ)。どのサーバが受けても同じように処理でき、1台が故障しても他のサーバが引き継げる。Webが世界規模に育てた立役者。
欠点毎回すべてを名乗る必要があり、送信データが増える。認証などの処理も毎回繰り返される。「ログインしたのに次のページで忘れられる」のでは困るため、状態が必要な場面では下記のCookieなどで補う。

Cookieとセッション — ステートレスなHTTPでログイン状態を保つ

「ログインしたままにする」機能は、HTTP自体を変えずに、ヘッダで会員証をやりとりすることで実現しています。

① ログイン情報を送る

POST /login HTTP/1.1
Host: www.example.com
Content-Type: application/x-www-form-urlencoded

username=hanako&password=secret123

② サーバが「会員証」(セッションID入りCookie)を発行する

HTTP/1.1 200 OK
Set-Cookie: session_id=xg93k2f8a1; HttpOnly; Secure
Content-Type: text/html; charset=utf-8

(ログイン後のページ)

③ 以後のリクエストでは、クライアントが毎回Cookieを提示する

GET /mypage HTTP/1.1
Host: www.example.com
Cookie: session_id=xg93k2f8a1

サーバは受け取ったセッションID(ログイン中の利用者を識別する合言葉)を手がかりに 「これは花子さんだ」と判断します。 リクエスト自体は相変わらず毎回完全な形で送られており、HTTPのステートレス性は保たれたまま、 その上に状態管理を載せているのがポイントです。

Cookieのやりとりが盗み見られるとログイン状態ごと乗っ取られます(セッションハイジャック)。 CookieにはHTTPS必須の Secure 属性などを付け、通信全体を後述のHTTPSで守るのが現在の常識です。

キャッシュと条件付きGET

同じ画像やページを毎回ダウンロードし直すのは無駄です。 そこでHTTPには、取得したリソースをクライアント側で保存して再利用するキャッシュ(cache)の仕組みが組み込まれています。 サーバはCache-Controlヘッダで再利用の条件を指示します。

「600秒間は再利用してよい」という指示付きのレスポンス

HTTP/1.1 200 OK
Content-Type: image/png
Cache-Control: max-age=600

(画像データ)

条件付きGET — 「変わっていたら」だけ送ってもらう

有効期限が切れたあとも、リソースが変わっていなければ再ダウンロードは不要のはずです。 そこで使うのが条件付きGETです。サーバはリソースの版を表すタグ(ETag)を発行し、 クライアントは「この版から変わっていたらください」と問い合わせます。

① 最初のレスポンスに版タグ(ETag)が付いてくる

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
ETag: "abc123"

(ページ本体 100KB)

② 2回目以降は「この版から変わっていたら」と条件を付けて聞く

GET /news/2026/07/ HTTP/1.1
Host: www.example.com
If-None-Match: "abc123"

③ 変わっていなければ、本体なしの304だけが返る

HTTP/1.1 304 Not Modified
ETag: "abc123"

③のレスポンスにはボディがありません。100KBの本体の代わりに数十バイトの「変わってないよ」だけが流れ、 クライアントは手元のキャッシュを表示します。 「変わっていなければ本体を送らない」——この節約が、世界中で膨大な通信量を削減しています。

更新日時で判定する方式(Last-Modified と If-Modified-Since)もあります。考え方は同じです。 ブラウザの開発者ツールのNetworkタブで、304がたくさん流れている様子を実際に観察できます。

HTTPS — 暗号化されたHTTP

HTTPのメッセージはただのテキストなので、そのまま流すと通信経路上で読めてしまいます。 そこで、TLS(Transport Layer Security)という暗号化の層をHTTPとTCPの間に挟んだのが HTTPS(HTTP Secure)です。HTTP自体の会話ルールは変わらず、通信路だけが保護されます。 HTTPSは次の3つを守ります。

盗聴の防止(暗号化)

経路上の第三者がメッセージを読めない。パスワードやカード番号、Cookieを守る。

改ざんの検知

途中でメッセージが書き換えられたら検知できる。広告の勝手な差し込みなども防ぐ。

なりすましの防止(証明書)

「本当に example.com のサーバか」をサーバ証明書で確認できる。偽サイトへの誘導を防ぐ。

書籍刊行の2010年ごろ、HTTPSは「ログインページと決済ページだけ」のものでした。 現在はすべてのページでHTTPSを使うのが事実上必須です。 ブラウザはHTTPのサイトに「保護されていない通信」と警告を出し、アドレスバーの鍵マークが標準の光景になりました。 転機は、証明書を無料で自動発行するLet's Encrypt(2016年正式サービス開始)の登場です。 また、後述のHTTP/2以降は主要ブラウザが事実上HTTPSでしか通信しないため、「暗号化は前提」の時代になっています。

持続的接続とリクエストの多重化

1つのWebページは、HTML本体だけでなくCSS・JavaScript・画像・Web APIのデータなど、 何十個ものリソースからできています。これらをいかに速く取りに行くかが、 HTTPの「運び方」の進化の歴史です。ここは「HTTP/1.1で次々にリクエストを送れるのか?」という疑問の答えになる節です。

持続的接続(keep-alive)— 接続を使い回す

HTTP/1.0では、リクエスト1つごとにTCP接続を開いて・使って・閉じるを繰り返していました。 接続を開く手続き(ハンドシェイク)は毎回それなりの時間がかかるので、リソースが多いページほど遅くなります。 HTTP/1.1では持続的接続(keep-alive)が既定になり、 1本のTCP接続を開いたまま、複数のリクエスト/レスポンスを続けてやりとりできるようになりました。 接続の開け閉めが減るぶん速くなります。

「レスポンスを待たずに次々に送れるか?」— パイプラインの理想と現実

ご質問の核心です。HTTP/1.1にはパイプライン(pipelining)という仕組みが仕様上あり、 1本の接続で、前のレスポンスを待たずにリクエストを連続で送ることが「一応」できます。 ところが、これはほとんど使われていません。理由はレスポンスを送った順に返さなければならないという決まりです。

1列のレジにたとえると。 パイプラインは「注文を先にまとめて全部言う」ようなものですが、 商品は注文した順にしか出てこない決まりです。 先頭の注文が時間のかかる品だと、後ろの軽い注文まで全部つかえて待たされます。 これをヘッドオブラインブロッキング(先頭詰まり)と呼びます。 この弱点と実装の不具合のため、主要ブラウザはパイプラインを既定で無効にしており、事実上の廃止状態です。

では実際の「並列」はどうやって? — 複数接続と多重化

「画像やデータを同時並行で取りに行く」という体感は本物です。ただしその実現方法がバージョンで違います。

方式接続の数待たずに送れる?順不同で受け取れる?実際の利用
逐次(HTTP/1.1 keep-alive)1本を使い回す×(1往復ずつ)×基本形
パイプライン(HTTP/1.1)1本○(連続送信)×(送った順に返る=先頭詰まり)ほぼ使われない
並列接続(HTTP/1.1)複数(1オリジンあたり6本程度)○(接続ごとに独立)△(接続をまたげば同時)HTTP/1.1の実際の並列手段
多重化(HTTP/2以降)1本○○(順不同で同時)現在の主流

つまりHTTP/1.1では、ブラウザは1つのサーバに対してTCP接続を複数本(6本程度)張り、 そこに画像やCSSのリクエストを振り分けることで並列化していました(パイプラインではなく複数接続で並列にしていた)。 HTTP/2ではこれが洗練され、1本の接続の中で、多数のリクエスト/レスポンスを順不同で同時にやりとりする「多重化」が実現し、 先頭詰まりの問題も(HTTPの層では)解消されました。

ご質問の2つのイメージへの答え。
・「ページ表示が半端な状態ごとに別のページへ遷移していくイメージ?」→ いいえ。 持続的接続は1つのページを構成する多数の部品(画像・CSS・JS・APIデータ)を効率よく取りに行く話で、ページの遷移とは無関係です。
・「画像の表示・データ取得を並列で処理依頼するイメージ?」→ はい、そちらが正解に近いです。 1ページ内の多数のリソースを同時並行で取得します。HTTP/1.1では複数のTCP接続で、HTTP/2以降は1接続の多重化で並列化します。

「半端な状態」の正体は、接続ではなくレンダリング。 ページが少しずつ表示されていく(まず文字、次に画像…)のは、 ブラウザが届いたリソースから順に画面を組み立てていく「段階的レンダリング」の働きで、接続の使い回しとは別の話です。 「通信の並列化(接続の話)」と「表示の段階的な組み立て(描画の話)」を分けて捉えると、混乱しません。 実際の通信の並列の様子は DevToolsのNetworkパネルの Waterfall で見られます。

HTTPのバージョンの歴史

バージョン年特徴
HTTP/0.91991最初の実装。GETしかなく、ヘッダもステータスコードもない「HTMLを取ってくるだけ」の仕組み。
HTTP/1.01996ヘッダ・ステータスコード・POSTなどが加わり、ほぼ現在の形に。ただし1リクエストごとにTCP接続を張り直す。
HTTP/1.11997接続を使い回すkeep-alive(持続的接続)が標準になり高速化。Hostヘッダ必須化。書籍が解説する版で、20年以上主役だった。
HTTP/220151本のTCP接続で複数のリクエスト/レスポンスを並行して流せる多重化。テキストからバイナリ形式になり、ヘッダも圧縮。
HTTP/32022土台をTCPからQUIC(UDPベースの新しいトランスポート)に変更。接続開始が速く、モバイル回線の切り替えにも強い。

バージョンが上がって変わったのは運び方(速さ・効率)だけです。 GETやPOSTというメソッドの意味も、404や200というステータスコードの意味も、ヘッダの役割も変わっていません。 だからこのページで学んだ知識は、HTTP/1.1でもHTTP/3でもそのまま通用します。 「意味の層は不変、転送の層だけ世代交代」——これがHTTPの歴史の読み方です。
