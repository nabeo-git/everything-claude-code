CLI診断ツール — Windows と Linux で「どの層の何を」確認する

このページは診断ツール編(実作業編)です。 OSに最初から入っているコマンドで、ネットワークとHTTPを切り分ける方法を、 Windows(PowerShell + 従来コマンド)と Linux の両方で、レイヤ別に整理します。 各ツールについて「どの層の・何を・なぜ確認するのか」を必ず添えます。 ブラウザで見る場合は DevToolsのページ、 切り分けの順番の考え方は 経路とエラーのページを参照してください。

「サイトにつながらない」「遅い」「APIが変な応答を返す」——原因を突き止めるには、 下の層(本当に届いているか)から順に、一枚ずつ確かめて上の層(HTTP)へ登っていくのが鉄則です。 どのコマンドも「ネットワークのどの層を照らす懐中電灯なのか」を意識すれば、闇雲に叩かずに済みます。 まずは全体地図から見ていきましょう。

切り分けのためのレイヤ地図

ネットワークは層(レイヤ)で積み上がっています。下ほど基礎で、上ほどアプリケーションに近い話です。 トラブルの切り分けは、下の層から「ここは正常」と確認して上へ登るのが基本です (下が壊れていれば、上は必ず失敗するからです)。

アプリケーション(L7) HTTP / TLS 実際のHTTPのやりとりと暗号化。curl / Invoke-WebRequest / openssl s_client。→ HTTP節 / TLS節
名前解決 DNS ドメイン名 → IPアドレスの変換。技術的にはアプリ層のサービスだが、切り分けでは独立した確認項目。dig / nslookup / Resolve-DnsName。→ DNS節
トランスポート(L4) TCP / UDP + ポート番号 相手の特定のポートに通信路を張れるか。Test-NetConnection -Port / nc -vz / ss。→ ポート節
インターネット(L3) IP / ICMP 相手のホストまでパケットが届くか、どの経路を通るか。ping / traceroute。→ 到達性節
リンク(L2/L1) イーサネット / Wi-Fi 自分のIP設定・経路・隣接機器。ipconfig / ip addr / arp。

タスク別クイックインデックス

  • そもそもつながらない → まず IP到達性(ping)
  • 名前解決を疑う(IPなら通るのに名前だと駄目) → DNS
  • ホストには届くがポートが開いているか不明 → ポート到達性
  • HTTPS/証明書の警告 → TLS/証明書
  • HTTPの中身(ステータス・ヘッダ・ボディ)を見たい → HTTP取得
  • 上のツールで切り分かない → パケットキャプチャ

1. IP到達性(L3 / ICMP)— そもそも届くか、どこで止まるか

対象レイヤ: インターネット層(L3、IP/ICMP)。 何を見る: 相手ホストまでパケットが往復できるか(ping)、 途中のどの中継点(ホップ)まで進めるか(traceroute系)。

Windows(PowerShell / コマンド)

# 届くか(ICMP ping)
ping example.com
Test-Connection -TargetName example.com -Count 4

# 経路をたどる
tracert example.com
Test-NetConnection example.com -TraceRoute

# 経路 + 各ホップの遅延・損失(時間はかかる)
pathping example.com

# 自分のIP・ゲートウェイ・DNS設定
ipconfig /all
Get-NetIPConfiguration

Linux

# 届くか(ICMP ping)。Ctrl+C で停止
ping example.com

# 経路をたどる
traceroute example.com
tracepath example.com

# 経路 + 損失を継続表示(見やすい)
mtr example.com

# 自分のIP・経路
ip addr
ip route

目的: HTTP以前に、ネットワークとして相手に届いているのかを確かめること。 分かること・次の一手: ping が返れば L3 は生きている——問題はより上の層(ポートやHTTP)にある。 返らない/途中のホップで止まるなら、その先の経路やファイアウォールの遮断を疑う (→ 経路とエラー:DROP は無反応=タイムアウト)。

ping が返らない=障害、とは限りません。 セキュリティ上、ICMP(ping)だけをわざと遮断しているサーバやFWは珍しくありません。 「ping は駄目だが Web は見える」ことは普通に起こります。ping はあくまで最初の目安で、 最終判断は上の層(ポート/HTTP)の確認と合わせて行います。

2. 名前解決(DNS)— ドメイン名は正しいIPに変換されているか

対象レイヤ: DNS(名前解決。技術的にはアプリ層のサービス)。 何を見る: example.com のようなドメイン名が、どのIPアドレスに変換されるか。 どのDNSサーバに聞いているか、キャッシュに古い値が残っていないか。

Windows(PowerShell / コマンド)

# 名前 → IP を引く
nslookup example.com
Resolve-DnsName example.com

# 使っているDNSサーバの確認
Get-DnsClientServerAddress

# DNSキャッシュの表示 / 消去
ipconfig /displaydns
ipconfig /flushdns

Linux

# 名前 → IP を引く
dig example.com
dig +short example.com
host example.com

# OSの名前解決順序(hosts等)も含めて引く
getent hosts example.com

# systemd-resolved 環境
resolvectl query example.com

目的: 「IP直打ちなら通るのに、ドメイン名だと駄目」というときに、変換そのものを疑うこと。 分かること・次の一手: 返ってくるIPが期待通りか/そもそも引けているかが分かります。 引けない・古いIPが返るなら、DNS設定やキャッシュ(flushdns)の問題。 正しいIPが引けているのに繋がらないなら、原因はポートやHTTP側にある、と切り分けられます。

3. ポート到達性(L4 / TCP)— 相手の窓口に通信路を張れるか

対象レイヤ: トランスポート層(L4、TCP/UDP + ポート番号)。 何を見る: 相手の特定のポート(例:HTTPSの443)にTCP接続が張れるか。 ping(L3)が通っても、ポートがFWで塞がれていれば通信は成立しません。ここはその一段上の確認です。

Windows(PowerShell / コマンド)

# 主役: 443番へTCP接続できるか
Test-NetConnection example.com -Port 443
# → TcpTestSucceeded : True なら開通

# 詳細表示(経路・IP・応答も)
Test-NetConnection example.com -Port 443 `
  -InformationLevel Detailed

# よく使うポートは名前指定も可
Test-NetConnection example.com -CommonTCPPort HTTP

# 今つながっている接続の一覧
Get-NetTCPConnection -State Established
netstat -ano

Linux

# 443番へTCP接続できるか(-z:送らず確認, -v:詳細)
nc -vz example.com 443

# telnet でも可(つながれば画面が変わる)
telnet example.com 443

# bash 組み込み(nc が無い環境で)
echo > /dev/tcp/example.com/443 && echo OPEN

# 待ち受け/接続中のポート一覧
ss -tulpn
netstat -tulpn

目的: 「ホストには届く(ping OK)のに、そのサービスにつながらない」ときに、ポートの開通を確かめること。 分かること・次の一手: TCPが張れれば、経路とポートは正常——問題はTLSかHTTPなど、より上の層。 張れない(タイムアウト/拒否)なら、FWでそのポートが遮断されている可能性が高い (→ 経路とエラー:REJECT は即拒否、DROP はタイムアウト)。

ポートスキャン(nmap 等)は相手を選ぶこと。 nmap のように多数のポートを一括で調べるツールは強力ですが、 自分が管理する/許可を得た対象にのみ使ってください。無関係なサーバへのスキャンは、 攻撃の偵察とみなされ得ます。単一ポートの疎通確認なら上記の Test-NetConnection / nc で十分です。

4. 暗号化(TLS / 証明書)— HTTPSが正しく成立するか

対象レイヤ: 暗号化(TLS)(TCPとHTTPの間)。 何を見る: TLSハンドシェイクが成功するか、サーバ証明書は誰が発行した何者で、有効期限内か、 使われているプロトコル版・暗号方式。

Windows(PowerShell / コマンド)

# 本物の curl で詳細表示(TLSの様子も出る)
curl.exe -v https://example.com/

# TCP到達性まではこれで(TLS内容は見ない)
Test-NetConnection example.com -Port 443

# 証明書を視覚的に見るなら
#   ブラウザの DevTools → Security パネル
#   (鍵マーク → 証明書の詳細)

Linux

# TLSハンドシェイクと証明書チェーンを表示
openssl s_client -connect example.com:443 \
  -servername example.com

# 証明書の有効期限だけ取り出す
echo | openssl s_client -connect example.com:443 \
  -servername example.com 2>/dev/null \
  | openssl x509 -noout -dates

目的: ブラウザの「保護されていない通信」「証明書エラー」の正体を特定すること。 分かること・次の一手: 「証明書の期限切れ/ドメイン名の不一致/中間証明書の欠落」などが具体的に分かります。 -servername(SNI)を付けるのは、1つのIPで複数サイトを配信する現代のサーバに正しいサイトの証明書を出させるためです。 ブラウザで手早く見たいときは DevTools の Security パネルが便利です。

5. HTTP(L7)— 応答のステータス・ヘッダ・ボディを取得する

対象レイヤ: アプリケーション層(HTTP)。 何を見る: 実際のHTTPリクエストを投げて、ステータスコード・ヘッダ・ボディを受け取る。 ここまで来れば、下の層はすべて正常という前提で「HTTPそのもの」を調べられます。

Windows(PowerShell)

# ヘッダと本文(ステータス・ヘッダを持つオブジェクト)
Invoke-WebRequest https://example.com/

# ヘッダだけ確認(HEAD)
Invoke-WebRequest https://example.com/ -Method Head

# JSON APIは自動でオブジェクトに変換される
Invoke-RestMethod https://example.com/api/items

# 本物の curl も使える(Windows 10 以降同梱)
curl.exe -v https://example.com/

Linux

# 生のやりとりを詳細表示
curl -v https://example.com/

# ヘッダだけ(HEAD)
curl -I https://example.com/

# どの段階で時間がかかるか計測
curl -o /dev/null -s \
  -w 'connect=%{time_connect} total=%{time_total}\n' \
  https://example.com/

# wget でヘッダを見る
wget -S -O /dev/null https://example.com/

目的: ブラウザを介さず、HTTPの応答そのもの(成功か、リダイレクトか、4xx/5xxか)を確かめること。 分かること・次の一手: ステータスとヘッダから、 4xx(依頼側/ポリシー)か 5xx(サーバ側/経路)か、 どの中継装置が返したか(Via / Server ヘッダ)が読めます。ここは DevTools の Network パネルと同じ情報を、コマンドで得ている形です。

PowerShell の curl は本物とは限りません。 Windows PowerShell では curl と wget が Invoke-WebRequest の別名(エイリアス)になっていることがあります。 本物の curl を使いたいときは、必ず curl.exe と拡張子まで書いて呼び分けてください。

6. パケットキャプチャ(全層)— 最後の手段として生の通信を見る

対象レイヤ: すべての層(実際に流れているパケットそのもの)。 何を見る: ネットワークを流れる生のパケットを捕まえて記録し、後から1つずつ中身を確認する。

Windows

# 標準搭載のパケットモニタ
pktmon start --capture
pktmon stop
#   → 記録を pcapng に変換して Wireshark で解析

# 定番GUIツール(要インストール)
#   Wireshark

Linux

# 特定ホストの通信だけ記録
sudo tcpdump -i any host example.com -w cap.pcap

# 画面で流し見(HTTPポート)
sudo tcpdump -i any port 80 -A

目的: 上のツール(ping〜curl)で切り分けきれない込み入った問題の最終確認。 「TCPのやりとりのどこで切れたか」「再送が多いか」など、他のツールでは見えない挙動を直接観察できます。 分かること・次の一手: 通信の生の流れが分かるため確実ですが、読み解きに知識が要る上級ツールです。 まずは 1〜5 のツールで層を絞り込み、どうしても分からないときにここへ来る、という順番が効率的です。

この順番こそが「迷わない」コツです。 到達性(L3)→ 名前解決(DNS)→ ポート(L4)→ TLS → HTTP(L7)と、 下から一枚ずつ「ここは正常」を確定していけば、問題は必ずどこかの層で特定できます。 エラーメッセージを睨むより、この順で潰すほうが速く確実です。 切り分けの具体的な進め方は 経路とエラー:原因の調べ方も参照してください。
