API設計 — Web APIを設計する

ここまでに学んだURI・HTTP・JSON・RESTを総動員して、いよいよ自分でWeb APIを設計する実践編です。 このページでは架空の「オンライン書店API」を題材に、機能の整理からエラー設計までを通しで実演します。 設計と言っても難しい話ではありません。要は「使う人が迷わない住所と作法を決めること」です。 書籍『Webを支える技術』第5部「Webサービスの設計」に対応する内容です。

良いWeb APIとは

Web APIを使うのは人間ではなくプログラム——正確には、そのプログラムを書くプログラマです。 つまりAPI設計とは、プログラマという「利用者」のためのユーザインターフェース設計です。 良いAPIの条件は次の3つに集約されます。

予測できる

一部を見れば残りの使い方を推測できる。RESTの統一インターフェースに従うことがその近道。

覚えやすい

短く一貫したURIと命名。例外や特別ルールが少ないほど、ドキュメントを読み返す回数が減る。

壊れない

一度公開したURIと仕様を変えない。クールURI(変わらないURI)の考え方をAPIにも適用する。

APIは一度公開すると、世界中の見知らぬプログラムがそれに依存し始めます。 Webサイトのデザインは明日変えられますが、APIの設計ミスは「使っている全プログラムの修正」を意味するため、後から直すのが非常に困難です。 だからAPIこそ、最初の設計が大事なのです。

設計の手順 — 6つのステップ

Web API設計は、次の6ステップで進めるのが定石です。

  1. 提供する機能の整理 利用者に何をさせたいかを列挙する。例:「本を検索する」「本の詳細を見る」「レビューを読む・投稿する」。
  2. リソースの洗い出し 機能を「モノ(名詞)」に変換する。「本を検索する」→ 書籍というリソース、「レビューを投稿する」→ レビューというリソース。
  3. URI設計 各リソースに住所を付ける。/books、/books/42、/books/42/reviews のように。
  4. メソッド割り当て 各URIに GET/POST/PUT/DELETE のどれを許すかを決め、リソース×メソッドの表を作る。
  5. 表現(JSON)設計 レスポンスとリクエストボディのフィールド名・型・日付形式などを決める。
  6. エラー設計 失敗時にどのステータスコードで、どんなエラー情報を返すかを決める。

以降のセクションでは、架空のオンライン書店API(api.example.com)を題材に、 ステップ3〜6を順に実演していきます。

URI設計のベストプラクティス

URIはAPIの「顔」です。基本原則はシンプルで、URIは名詞(リソース)、動詞(操作)はHTTPメソッドに任せる—— これだけで大半の設計判断が決まります。定番のルールを良い例・悪い例で見てみましょう。

ルール良い例悪い例悪い理由
名詞・複数形で表す GET /books GET /getBookList 動詞入り。操作はメソッド(GET)がすでに表しているので二重になる。
個別リソースはIDで指す GET /books/42 GET /book.php?id=42 実装技術(.php)が漏れている。実装を変えたらURIが壊れる。
階層は「所属関係」を表す GET /books/42/reviews GET /reviews?bookId=42 誤りではないが、「書籍42に属するレビュー」という関係は階層で表す方が読み取りやすい。
動詞を入れない DELETE /books/42 POST /deleteBook 削除の意味は DELETE メソッドが持っている。URIに動詞を入れると統一インターフェースが崩れる。
絞り込み・並び替えはクエリで GET /books?author=yamamoto&sort=year GET /books/author/yamamoto/sort/year 検索条件はリソースの階層ではなく「選び方の指定」。クエリパラメータ(→ URIのページ)の出番。

複数形(/books)を使うのは、「books というリソースの集まり(コレクション)があり、 その中の1件が /books/42」という親子関係が自然に読めるからです。 小文字・ハイフン区切り(例: /best-sellers)で統一するのも定番です。

メソッド割り当てと表現設計

URIが決まったら、各URIに許すメソッドを表にします。この表がそのままエンドポイント一覧 (エンドポイント = APIの窓口となる個々のURI)になり、APIの全体仕様の骨格です。

エンドポイントGETPOSTPUTDELETE
/books 書籍の一覧・検索 書籍の新規登録 — —
/books/42 書籍42の取得 — 書籍42の更新 書籍42の削除
/books/42/reviews 書籍42のレビュー一覧 レビューの投稿 — —
/books/42/reviews/7 レビュー7の取得 — レビュー7の更新 レビュー7の削除

実例① 検索 — GET /books?q=web(ページネーション付き)

一覧系のAPIでは、結果を小分けにして返すページネーション(pagination、ページ分割)が必須です。 何万件もの結果を一度に返すと、サーバもクライアントもパンクするからです。

リクエスト(検索+ページ指定)

GET /books?q=web&page=1&per_page=20 HTTP/1.1
Host: api.example.com
Accept: application/json

レスポンス(件数情報付きの一覧)

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "total": 42,
  "page": 1,
  "per_page": 20,
  "books": [
    {
      "id": 42,
      "title": "Webを支える技術",
      "author": "山本陽平",
      "published_on": "2010-04-08"
    },
    {
      "id": 57,
      "title": "はじめてのWeb API",
      "author": "example出版編集部",
      "published_on": "2024-11-01"
    }
  ]
}

実例② レビュー投稿 — POST /books/42/reviews

リクエスト(投稿内容をJSONで)

POST /books/42/reviews HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "rating": 5,
  "comment": "Webの全体像がつながりました"
}

レスポンス(201 Created + Location)

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: https://api.example.com/books/42/reviews/8

{
  "id": 8,
  "rating": 5,
  "comment": "Webの全体像がつながりました",
  "created_at": "2026-07-19T09:30:00+09:00"
}

表現(JSON)設計の定番ルール

項目定番のやり方
ページネーション page / per_page 方式(ページ番号)か、limit / offset 方式(先頭からの位置)。どちらでもよいがAPI全体で統一する。
日付・時刻 ISO 8601形式(例: 2026-07-19T09:30:00+09:00)。世界中のプログラミング言語がそのまま解釈できる国際標準。
フィールド命名 created_at(スネークケース)か createdAt(キャメルケース)かは好みでよいが、混在させない。一貫性そのものが仕様。

エラー設計

エラーのときこそAPIの品質が問われます。原則は2つ。 ①ステータスコードで「失敗の種類」を正しく伝える、 ②ボディで「何が悪かったか」を機械にも人間にも分かる形で伝える。 使い分けの定番は次のとおりです(コード体系の全体像は → HTTPのページ)。

コード名前いつ使うか書店APIでの例
400 Bad Request リクエストの形式が壊れている ボディのJSONが文法エラーで解析できない
401 Unauthorized 認証されていない(あなたが誰か分からない) トークンなしでレビューを投稿しようとした
403 Forbidden 認証済みだが権限がない(誰かは分かるがダメ) 他人のレビューを削除しようとした
404 Not Found リソースが存在しない GET /books/9999(そんな本はない)
422 Unprocessable Content 形式は正しいが内容が検証エラー rating に 6 を指定した(1〜5のはず)
500 Internal Server Error サーバ側の予期しない障害(クライアントは悪くない) データベースが落ちていた

エラーレスポンスの例(検証エラー)

HTTP/1.1 422 Unprocessable Content
Content-Type: application/json; charset=utf-8

{
  "error": "validation_failed",
  "message": "rating は 1〜5 の整数で指定してください",
  "field": "rating"
}

ありがちな失敗が「何が起きても 200 OK を返し、ボディの中に "success": false と書く」設計です。 これではキャッシュや監視ツールなどHTTPを理解する道具がエラーを検知できず、 RESTのページで学んだ「Webのインフラに乗れる」利点を自ら捨てることになります。

エラーボディの形式は長らく各社バラバラでしたが、現在はRFC 9457「Problem Details for HTTP APIs」という標準形式があります。 Content-Type: application/problem+json を使い、決まったフィールド名で問題を記述します。新規設計なら採用を検討する価値があります。

RFC 9457形式のエラーレスポンス

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/validation-failed",
  "title": "入力値が正しくありません",
  "status": 422,
  "detail": "rating は 1〜5 の整数で指定してください"
}

変化に耐える設計 — バージョニングと後方互換性

APIは公開した瞬間から「変えられないもの」になりますが、サービスは成長し、仕様変更は必ず起きます。 そこで、変化に備える仕掛けをあらかじめ組み込んでおきます。

バージョニング

バージョニング(versioning)とは、APIの版数をURIなどに含めて、 新旧の仕様を並行運用できるようにすることです。 主流はURIにバージョンを入れる方式で、一目で分かり、試しやすいのが利点です。 

https://api.example.com/v1/books/42   ← 現行版
https://api.example.com/v2/books/42   ← 大きな仕様変更をした新版(v1も当面残す)

URIバージョニングの例。ヘッダで指定する方式(例: Accept: application/vnd.example.v2+json)もある

後方互換性

後方互換性(backward compatibility)とは、「昔から使っているクライアントが壊れずに動き続けること」。 変更には安全なものと危険なものがあります。

変更の種類安全?理由
レスポンスへのフィールド追加 安全 既存クライアントは知らないフィールドを無視すればよい。
フィールドの削除・改名 破壊的変更 そのフィールドを読んでいたクライアントが即座に壊れる。
フィールドの意味や型の変更 破壊的変更 見た目は動き続けるのに結果が狂う、最も発見しにくい壊れ方をする。

まとめると、「追加は自由、削除と変更はバージョンアップ(v2)の仕事」が原則です。 そしてバージョンアップしても古いURIをすぐには消さない——これは URIのページで学んだクールURI(URIは変わらない・壊さない)のAPI版の実践です。

認証とセキュリティ(さわりだけ)

実際のAPIでは「誰からのリクエストか」を確認する認証(authentication)が必要になります。 代表的な方式だけ、名前と雰囲気を押さえておきましょう。

APIキー

利用者ごとに発行される合言葉の文字列。ヘッダに載せて送る。簡易だが、利用者の識別と利用量の管理には十分。

Bearerトークン

ログイン後に発行される「持参人有効の通行証」。Authorization ヘッダに載せる(下の例)。現在のAPIで最も一般的。

OAuth 2.0

「他サービスに、自分の代わりに安全に権限を委ねる」ための標準の仕組み。パスワードを渡さずに連携できる。

Bearerトークンを付けたリクエストの例

GET /books/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjMifQ.(以下略)

認証情報は平文のHTTPで送ると盗聴で漏れます。だからこそ現在のAPIはHTTPS(TLSで暗号化されたHTTP)が必須です(→ HTTPのページ)。 なお、認証・認可の仕組みは本サイトの範囲を超える深いテーマなので、ここでは「そういう部品がある」という紹介にとどめます。

最新動向: OpenAPI(Swagger)

設計したAPIをどう文書化するか。現在の標準はOpenAPI(旧称Swagger)です。 OpenAPIは「APIの仕様書を機械可読(プログラムが読める形式)に書くための標準」で、 YAMLまたはJSONで記述します。書店APIの一部を書くとこうなります。

書店APIの一部をOpenAPI(YAML)で記述した断片

openapi: 3.1.0
info:
  title: オンライン書店API
  version: 1.0.0
paths:
  /books/{bookId}:
    get:
      summary: 書籍を1冊取得する
      parameters:
        - name: bookId
          in: path
          required: true
          schema:
            type: integer
      responses:
        "200":
          description: 書籍の情報
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Book"
        "404":
          description: 指定した書籍が存在しない

仕様書が機械可読になると、読めるドキュメントの自動生成、クライアント/サーバのコードの自動生成、 本物のサーバなしで試せるモック(模擬サーバ)の作成までツールに任せられます。 現在の実務では「まずOpenAPIで仕様を書き、それを起点に開発する」流れが広く定着しています。 このページで学んだ設計手順は、そのままOpenAPIに書き下ろす内容そのものです。
