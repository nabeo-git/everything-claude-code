HTTP・URI・HTML・REST — まず「全体の地図」を手に入れよう

Webの勉強を始めると、HTTP、URI、HTML、REST、JSON、Ajax……と用語が次々に出てきて、 「それぞれが何で、どう関係しているのか」が分からなくなりがちです。 このサイトは、書籍『Webを支える技術』(山本陽平 著)の内容をベースに、 これらの用語をひとつの技術体系の地図として整理し、 最新のWeb事情も踏まえて初級者向けに解説します。 このページはその地図の「全体図」です。細かい話に入る前に、まずここで位置関係をつかみましょう。

4つのキーワードを一言ずつで言うと

最初に結論だけ並べます。今は「ふーん」で構いません。このページを読み終わるころには意味がつながります。

URI

Web上の情報(リソース)の「住所」。
例: https://example.com/users/123

HTTP

その住所とデータをやりとりする「通信の手順(プロトコル)」。
例: GET /users/123 HTTP/1.1

HTML

やりとりされる「中身」の書き方のひとつ(人間がブラウザで読むページ用)。
例: <h1>プロフィール</h1>

REST

URI・HTTP・HTML(やJSON)をどう組み合わせて設計するかの「考え方」。モノではなく設計スタイル。

4つは「同じ種類のものの選択肢」ではありません。役割がまったく違う部品と、その組み合わせ方です。 「URI か HTTP か」のような二者択一の関係ではなく、全部が同時に、別の役割で使われています。 これが本サイト全体を貫くいちばん大事な視点です。

宅配便にたとえて理解する

Webでの1回のやりとりは、宅配便で荷物を送ってもらうことによく似ています。

URI = 宛先の住所

「どこの・何を」を世界中で一意に指し示す。住所が正確なら、誰が書いても同じ場所に届く。

HTTP = 配送のルール

伝票の書き方、「取りに行く(GET)/送る(POST)」などの依頼の種類、不在時(エラー時)の扱いまで決めた共通ルール。

HTML / JSON = 荷物の中身

箱の中身そのもの。人間向けの手紙がHTML、機械(プログラム)向けの部品がJSON、と考えると近い。

REST = 配送網の設計方針

「住所の付け方を統一する」「依頼の種類を共通化する」など、配送網全体がシンプルに回るようにする設計指針。

重要なのは、住所(URI)・配送ルール(HTTP)・中身(HTML/JSON)は別のものだということです。 住所が同じでも中身は変えられますし、同じ配送ルールでどんな中身でも運べます。 Webも同じで、この「役割の分離」こそがWebが世界規模に成長できた理由です。 なお、たとえはあくまで入り口です。正確な定義は各ページで確認してください。

技術スタック図 — どの層に何がいるか

Webの技術は、役割ごとに層(レイヤ)に分けて整理できます。上から「誰が使うか」→「何を」→「どこの」→「どうやって」の順です。

利用者 ブラウザ / スマホアプリ / プログラム Webを利用する側(クライアント)。人間だけでなくプログラムも利用者になる。
設計思想 REST 下の3層を「どう組み合わせてWebサービス/Web APIを設計するか」の指針。層というより、全体にかかる方針。→ RESTのページ
表現(何を) HTML / CSS / JavaScript / JSON / 画像・動画 やりとりされるデータの形式。人間向けの表現がHTML、プログラム向けの代表がJSON。→ HTML / Ajax
識別(どこの) URI (URL) 世界中のリソースに一意な名前(住所)を付ける仕組み。→ URIのページ
転送(どうやって) HTTP / HTTPS URIで示された場所とデータをやりとりする通信プロトコル。HTTPSは暗号化されたHTTP。→ HTTPのページ
基盤 TCP/IP・DNS・TLS インターネットそのものの土台。HTTPはこの上に乗っている(詳細はHTTPのページで少しだけ扱います)。

書籍『Webを支える技術』は、Webを支える最も基本的な技術として 「HTTP」「URI」「HTML」の3つを挙げ、その全体をまとめる設計思想としてRESTを解説しています。 この図はまさにその構図です。REST以外は「実物のある技術」、RESTだけは「考え方」である点に注目してください。

比較表 — 何が違うのか

キーワード ひとことで言うと 分類 具体例 主な標準・出典
URI 情報の「住所」(識別子) 命名・識別の仕組み https://api.example.com/users/123 RFC 3986 / WHATWG URL Standard
HTTP 住所とやりとりする「配送手順」 通信プロトコル GET /users/123 HTTP/1.1 RFC 9110〜9114(HTTP/1.1〜HTTP/3)
HTML 人間向けの「中身」の書き方 マークアップ言語(データ形式) <h1>こんにちは</h1> HTML Living Standard(WHATWG)
JSON プログラム向けの「中身」の書き方 データ形式 {"id": 123, "name": "佐藤"} RFC 8259
REST 全体をうまく組み合わせる「設計の考え方」 アーキテクチャスタイル 「リソースにURIを付け、HTTPの決まったメソッドで操作する」という方針 Roy Fielding の博士論文(2000年)

「分類」の列がすべて違うことに注目してください。比較表の形にしましたが、実際には比べるものではなく、重ねて使うものです。 たとえば「REST API」とは、「URIとHTTPとJSON(など)を、RESTの考え方に沿って組み合わせて作ったWeb API」のことです。

ブラウザでページが表示されるまでに起きること

全部の層が一度に働く様子を、実際の流れで見てみましょう。あなたがブラウザで https://example.com/news/2026/07/ を開いたとき、裏側ではこう動いています。

  1. URIの入力 アドレスバーのURLは「どのサーバの、どのリソースか」を示す住所(URI)。ブラウザはこれを分解して行き先を決める。
  2. DNSでサーバの居場所を調べる example.com というドメイン名を、ネットワーク上の住所(IPアドレス)に変換する。
  3. TCP接続とTLSハンドシェイク サーバと通信路をつなぎ、HTTPSなら暗号化の取り決め(TLS)も行う。ここまでが「電話をかけてつながった」状態。
  4. HTTPリクエストを送る 「このリソースをください(GET)」という依頼文(HTTPリクエスト)を送信する。
  5. HTTPレスポンスが返る サーバが「成功しました(200 OK)」という結果と、中身(HTML)を返す。
  6. HTMLを解析し、追加のリソースを取得 ブラウザはHTML内で参照されているCSS・画像・JavaScriptのURIに対して、さらにHTTPリクエストを繰り返す。
  7. 画面に描画。その後も同じことの繰り返し リンクをクリックすれば別のURIへ再びHTTPリクエスト。JavaScriptが裏でWeb APIを呼ぶ(Ajax)ときも、やっていることは同じ「URIへのHTTPリクエスト」。

手順4と5で流れるデータの実物は、たとえばこんなテキストです。

HTTPリクエスト(ブラウザ → サーバ)

GET /news/2026/07/ HTTP/1.1
Host: example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...
Accept: text/html,application/xhtml+xml,...
Accept-Language: ja,en;q=0.9

HTTPレスポンス(サーバ → ブラウザ)

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 5120
Cache-Control: max-age=600

<!DOCTYPE html>
<html lang="ja">
  <head><title>2026年7月のニュース</title></head>
  <body>
    <h1>2026年7月のニュース</h1>
    <a href="/news/2026/07/happy-web">Web学習サイトが公開されました</a>
  </body>
</html>

Webの通信は、突き詰めれば「URIに向かってHTTPリクエストを送り、レスポンスとして表現(HTMLやJSON)を受け取る」の繰り返しです。 どんなに複雑なWebサービスも、この1往復の積み重ねでできています。

WebサイトとWeb APIは「同じ仕組みの別の使い方」

初級者がつまずきやすいのが「WebサイトとWeb API(REST API)は別の技術なの?」という疑問です。 答えは「仕組みは同じ。返す中身と相手が違うだけ」です。同じユーザ情報を取得する2つのやりとりを見比べてください。

人間向け: Webサイト(HTMLを返す)

リクエスト

GET /users/123 HTTP/1.1
Host: www.example.com
Accept: text/html

レスポンス

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html>
<html lang="ja">
<body>
  <h1>佐藤花子さんのプロフィール</h1>
  <p>2024年4月に参加しました。</p>
</body>
</html>

プログラム向け: Web API(JSONを返す)

リクエスト

GET /users/123 HTTP/1.1
Host: api.example.com
Accept: application/json

レスポンス

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "id": 123,
  "name": "佐藤花子",
  "joined": "2024-04-01"
}

URI・HTTPメソッド・ステータスコードの使い方はまったく同じで、違うのは 返ってくる表現(HTMLかJSONか)と、それを読む相手(人間のためのブラウザか、プログラムか)だけです。 書籍『Webを支える技術』の言葉では、これは「同じリソースの異なる表現」にあたります。

書籍が書かれた2010年ごろはXMLも有力でしたが、現在のWeb APIの表現はJSONがほぼ標準です。 また、スマホアプリの裏側も実はほとんどがWeb API(HTTPS + JSON)で動いています。 「Webの技術=ブラウザの技術」ではなく、アプリやシステム連携を含むインターネット全体の共通基盤になっているのが現在地です。
