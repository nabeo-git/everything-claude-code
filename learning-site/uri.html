URI — リソースの住所

アドレスバーに表示される https://... という文字列。あれがURIです。 URIは、Web上のあらゆる情報に付けられた世界で一意な「住所」で、 Webの三本柱のうち「識別」を担当します。 このページでは、URIの土台にある「リソース」という考え方から、URIの構文の読み方、 そして「良いURIの付け方」までを学びます。 書籍『Webを支える技術』第2部「URI」に対応する内容です。

リソースという考え方

URIを理解する出発点は、URIそのものではなくリソース(resource)という言葉です。 リソースとは、Web上の情報の断片ひとつひとつのこと。 書籍『Webを支える技術』はこれを「Web上に存在する、名前を持ったありとあらゆる情報」と説明しています。 たとえば、次のものはすべてリソースです。

東京の今日の天気予報

https://example.com/weather/tokyo/today

商品番号4649の商品情報

https://shop.example.jp/items/4649

ユーザ123のプロフィール

https://example.com/users/123

2026年7月のニュース一覧

https://example.com/news/2026/07/

そしてURI(Uniform Resource Identifier)は、リソースに付けた名前です。 「統一的な(Uniform)・リソースの(Resource)・識別子(Identifier)」という名前のとおり、 世界中のどんな情報にも同じ形式で名前を付けられます。 名前が付いているからこそ、リンクで指し示したり、プログラムから取得したりできるのです。

リソースは「建物」、URIは「住所」だと考えてください。 住所が世界で一意だから、手紙(HTTPリクエスト)は迷わず届きます。 また、同じ建物に複数の住所(正面玄関と裏口)があってもよいように、 1つのリソースに複数のURIが付いていても構いません。 たとえば「今日の天気」と「2026年7月19日の天気」が同じ内容を指すことがあります。

「まず情報をリソースとして切り出し、それぞれにURIを与える」—— この発想がWebのすべての土台です。 後で学ぶRESTは、この「リソースにURIを付け、 HTTPの決まったメソッドで操作する」という設計の作法そのものです。

URI・URL・URNの違い

URIとよく似た言葉にURLがあります。関係を整理すると、 URIが総称で、URLとURNはその2つの方式です。

用語正式名指し方例
URIUniform Resource Identifier(識別子)総称。URLとURNをまとめた呼び名下の2つ両方
URLUniform Resource Locator(場所指定子)場所で示す。「どのサーバの、どのパスにあるか」https://example.com/users/123
URNUniform Resource Name(名前)名前で示す。場所が変わっても不変のIDurn:isbn:9784774142043(書籍のISBN番号)

URLは「住所で指す」方式なので、サーバの引っ越しなどで場所が変わるとたどれなくなる弱点があります。 URNはそれを補うために「場所と無関係な名前」を付ける方式です。 たとえば書籍のISBN番号は、その本がどこの書店・倉庫にあっても変わりません。

理屈はそうですが、現実のWebで使われているURIはほぼすべてURLです。 URNは名前を解決して実物にたどり着く仕組みが普及しなかったためです。 そのため日常会話では「URI」と「URL」はほぼ区別されずに使われます。 本サイトでは仕様書(RFC 3986)にならって「URI」と表記しますが、 「URLのことだな」と読み替えて問題ありません。

URIの構文を分解する

URIは一見ただの文字列ですが、決まった構文(書式)を持ちます。要素をすべて含んだ例で分解してみましょう。

https://user:pass@www.example.com:8080/users/123/posts?page=2&sort=new#comments
部品この例では役割
スキームhttpsアクセスの方式。https なら「暗号化したHTTPで取得する」という宣言。http、mailto、ftp なども。直後に :// が続く。
ユーザ情報user:pass接続に使うユーザ名とパスワード。末尾に @ を付ける。現在はセキュリティ上の理由でほぼ使われない(後述の注意を参照)。
ホストwww.example.comリソースを持つサーバの名前(ドメイン名)。インターネット全体で一意。DNSという仕組みでIPアドレスに変換される。
ポート番号:8080そのサーバの「窓口番号」。省略するとスキームごとの標準番号(デフォルトポート)が使われる。HTTPは80番、HTTPSは443番。
パス/users/123/postsサーバ内でリソースを指す階層的な道筋。フォルダ構造のように / で区切る。ホスト+パスでリソースが一意に決まる。
クエリ?page=2&sort=new追加の条件やパラメータ。? の後に「名前=値」を & でつないで並べる。検索条件やページ番号によく使う。
フラグメント#comments取得したリソースの内部の特定箇所を指す。ページ内の見出しへのジャンプなどに使う。サーバには送られず、クライアント側で解釈される。

つまりこのURIは「HTTPSという方式で、www.example.com というサーバの8080番窓口にある /users/123/posts というリソースを、2ページ目・新着順という条件付きで指し、 その中の comments という箇所を見る」という意味になります。

ふだん見かける https://www.example.com/users/123 のようなURIは、 ユーザ情報・ポート番号・クエリ・フラグメントを省略した形です。 ポート番号が書かれていなくても、裏では「HTTPSだから443番」と自動的に決まっています。

ユーザ情報(user:pass@)をURIに書く方式は、パスワードが丸見えになるため 現在は使ってはいけません。主要ブラウザも警告を出したり無視したりします。 認証情報はHTTPのAuthorizationヘッダなどで送るのが現在の作法です。

相対URIとベースURI

ここまでの「スキームから始まる完全な形」を絶対URIと呼びます。 一方、HTMLの中ではこんなリンクをよく見かけます。

HTML内の相対URIの例

<a href="../about">このサイトについて</a>

この ../about のように、途中から書き始める形を相対URIと呼びます。 ファイル操作の「1つ上のフォルダ」と同じ発想で、.. は「1階層上」を意味します。 相対URIは、基準となるURI(ベースURI)——通常は「今見ているページのURI」——と組み合わせて、 絶対URIに変換(解決)されます。

ベースURI(今いる場所)相対URI解決結果
https://example.com/users/123/profilepostshttps://example.com/users/123/posts(同じ階層)
../abouthttps://example.com/users/about(1つ上の階層へ)
/helphttps://example.com/help(/ 始まりはサーバのルートから)
#tophttps://example.com/users/123/profile#top(同じページ内の移動)

解決の手順はこうです。ベースURIの末尾のファイル名部分(profile)を取り除いて 「現在のフォルダ」/users/123/ を求め、そこを起点に相対URIをたどります。 ../about なら、1つ上の /users/ に移動してから about を付け、 /users/about になります。

相対URIの利点は、サイトのドメインが変わってもリンクを書き換えずに済むことです。 本サイト自身も、ページ間のリンクはすべて http.html のような相対URIで書かれています。

日本語とURI(%エンコーディング)

URIの仕様(RFC 3986)では、URIにそのまま使える文字が 英数字と一部の記号(- . _ ~ など)に制限されています。 世界中のどんなシステムでも安全に受け渡せるよう、最小公倍数の文字だけに絞っているのです。 では日本語のページ名はどうなるのでしょうか。実例を見てみましょう。

ブラウザのアドレスバーでの見た目

https://ja.wikipedia.org/wiki/寿司

実際に通信で使われるURI

https://ja.wikipedia.org/wiki/%E5%AF%BF%E5%8F%B8

「寿司」の部分が %E5%AF%BF%E5%8F%B8 という記号列に変わっています。 これが%エンコーディング(パーセントエンコーディング)です。 仕組みは単純で、文字を文字コード(通常UTF-8)のバイト列にし、 各バイトを「% + 16進数2桁」で書き表します。 「寿」はUTF-8で E5 AF BF の3バイトなので %E5%AF%BF、 「司」は E5 8F B8 なので %E5%8F%B8 になります。

最近のブラウザはアドレスバーで%エンコーディングを自動的に復元して「寿司」と表示してくれます。 しかし、アドレスバーからコピーしてテキストエディタに貼り付けると %E5%AF%BF... が現れることがあります。壊れているのではなく、それが本来の姿です。 検索フォームの送信後にURIへ付く ?q=%E5%AF%BF%E5%8F%B8 のようなクエリも同じ仕組みです。

良いURIの設計(クールURI)

URIは付ければよいというものではなく、設計の良し悪しがあります。 指針として有名なのが、Web発明者ティム・バーナーズ=リーの言葉 「Cool URIs don't change(クールなURIは変わらない)」です。 つまり、変わらないURIこそが良いURIだという原則です。

URIの例何が問題/何が良いか
悪い例https://example.com/cgi-bin/show_user.php?id=123実装技術(PHP、CGI)がURIに漏れている。サーバをPHPから別言語に作り替えた瞬間、このURIは死ぬ。
悪い例https://example.com/users/123?session=a8f3xk2zセッションID(ログインごとに変わる値)が入っている。同じリソースなのに毎回URIが変わり、ブックマークも共有もできない。
悪い例https://example.com/getUserInfo?id=123「取得する(get)」という動詞入り。操作の種類はHTTPメソッドの仕事であり、URIの仕事ではない。
良い例https://example.com/users/123シンプルで、実装技術に依存せず、リソースを名詞で表している。10年後も変えずに済む。

まとめると、良いURIの条件は次の3つです。

  1. 実装依存の情報を含めない .php、cgi-bin、servlet など、裏側の技術が変わると壊れる要素を入れない。
  2. セッションIDなど変動する値を含めない 同じリソースにはいつアクセスしても同じURIで届くようにする。
  3. リソースを名詞で簡潔に表す 「何をするか」(動詞)ではなく「何であるか」(名詞)を書く。短いほど覚えやすく、打ち間違いも減る。

なぜ「変わらない」ことがそこまで重要なのでしょうか。 Webの本質はリンクで情報をつなぐハイパーメディアであり、 世界中の無数のページ・ブックマーク・検索エンジンが、あなたのURIに向かってリンクを張るからです。 URIを変えることはそのリンクをすべてへし折る(リンク切れにする)ことを意味します。 URIはあなたのサイトの都合だけのものではなく、Web全体で共有される公共の資産なのです。

どうしてもURIを変更する場合の作法もあります。古いURIへのアクセスに対して 「301 Moved Permanently(恒久的に移転)」というステータスコードで新しいURIへ案内(リダイレクト)する方法です。 → HTTPのページで実例を見ます。

URIは誰が使うのか

最後に、URIが技術体系の中の「どこで」登場するのかを確認します。 URIは単独で働くのではなく、次の3つの文脈で他の技術に埋め込まれて使われます。

① HTMLのリンク先として(表現の中)

HTMLのハイパーリンク

<a href="https://example.com/users/123">佐藤さんのプロフィール</a>
<img src="/images/logo.png" alt="サイトロゴ">

href や src の値はすべてURIです。ハイパーメディアの「リンクの行き先」を担います。→ HTMLのページ

② HTTPリクエストの宛先として(転送の中)

HTTPリクエストライン

GET /users/123 HTTP/1.1
Host: example.com

HTTPリクエストの1行目には、URIのパス部分がそのまま書かれます(ホスト部分はHostヘッダに分けて書きます)。→ HTTPのページ

③ Web APIのエンドポイントとして(設計の中)

REST APIのエンドポイント設計の例

GET    https://api.example.com/v1/users/123        ユーザ123を取得
PUT    https://api.example.com/v1/users/123        ユーザ123を更新
DELETE https://api.example.com/v1/users/123        ユーザ123を削除

Web APIでは、プログラムがアクセスする窓口(エンドポイント)をURIで設計します。 同じURIに対して操作(メソッド)だけを変えるのがREST流の設計です。 具体的な設計手順はAPI設計のページで扱います。

現代のURI事情

書籍刊行(2010年)後のURIまわりのアップデートを3つ紹介します。

① WHATWG URL Standard — 現在のブラウザは、RFC 3986に加えて、実装の細部まで統一した 「URL Standard」(WHATWGが常時更新)に従ってURIを解釈しています。 歴史的な経緯から、この標準では「URI」ではなく「URL」という用語に一本化されています。

② 国際化ドメイン名(IDN) — ホスト名にも日本語などが使えるようになりました(例: 日本語.jp)。 内部ではPunycodeという方式で xn--wgv71a119e.jp のような英数字表現に変換されます。 %エンコーディングと同じく「見た目は多言語、通信路では制限された文字」という二段構えです。

③ プログラムでのURI操作 — JavaScriptには、URIを自前の文字列処理で切り貼りせずに済む URL オブジェクトが標準装備されました。

JavaScriptでURIをパースする例(表示のみ)

const url = new URL("https://www.example.com:8080/users/123?page=2#top");
console.log(url.protocol);  // "https:"
console.log(url.hostname);  // "www.example.com"
console.log(url.port);      // "8080"
console.log(url.pathname);  // "/users/123"
console.log(url.searchParams.get("page"));  // "2"
console.log(url.hash);      // "#top"

プロパティ名が、このページで学んだ構文の部品(スキーム・ホスト・ポート・パス・クエリ・フラグメント)と きれいに対応していることを確認してください。
