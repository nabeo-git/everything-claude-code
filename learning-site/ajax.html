Ajax — JavaScriptがHTTPを使う仕組み

ここまで、ブラウザがHTTPでHTMLを受け取る流れを学びました。 このページの主役は、その通信をJavaScriptが自分で行う仕組み = Ajax(エイジャックス)です。 検索の候補が打つそばから出てくるのも、地図がスルスル動くのも、裏でAjaxが働いています。 新しいプロトコルが登場するわけではありません。使うのはこれまで学んだHTTPそのものです。 「fetchのコード」と「実際に流れるHTTPメッセージ」を対応させながら見ていきます。

従来のWebとAjaxの違い

従来のWebでは、リンクをクリックするたび、フォームを送信するたびに、 ブラウザは画面全体を新しいHTMLで丸ごと置き換えていました。 Ajaxでは、JavaScriptが裏でHTTPリクエストを送り、返ってきたデータで画面の一部だけを書き換えます。

従来のWeb — 1クリックごとに全画面リロード

  1. ユーザがリンクやフォーム送信ボタンを押す 現在のページはここでいったん役目を終える。
  2. ブラウザがHTTPリクエストを送る 画面は白くなり、ユーザは待つ。
  3. サーバがページ全体のHTMLを返す 変わらない部分(ヘッダやメニュー)も毎回まるごと作り直して送る。
  4. ブラウザが画面全体を描画し直す スクロール位置も入力途中の内容もリセットされる。

Ajax — 裏で通信して一部だけ更新

  1. ユーザが操作する(文字を打つ、ボタンを押す) ページはそのまま表示され続ける。
  2. JavaScriptが裏でHTTPリクエストを送る 画面は固まらず、ユーザは操作を続けられる。
  3. サーバが必要なデータだけ(主にJSON)を返す ページ全体ではなく「候補リスト」「新着3件」など差分だけ。転送量が小さい。
  4. JavaScriptが画面の該当部分だけを書き換える ユーザには「ページの中身がぬるっと変わった」ように見える。

Ajaxが世界の注目を集めたのは2005年ごろ。地図を切れ目なくドラッグできるGoogle マップと、 入力のたびに候補が出る検索サジェストが「ページ遷移のないWeb」の衝撃を広め、 この手法にAjaxという名前が付きました(→ Webの歴史)。

従来のWebは「注文のたびに店員が新しいお膳を丸ごと運び直す定食屋」、 Ajaxは「追加の小鉢だけをさっと持ってきてくれる店」です。 運ぶ量が減るので速く、食事(ユーザの操作)も中断されません。

Ajaxの動作原理 — 4つのステップ

Ajaxは Asynchronous JavaScript + XML(非同期のJavaScriptとXML)の略です。 名前にXMLとありますが、現在やりとりされるデータはJSONが主流で、名前だけが当時のまま残っています。 鍵になるのは「非同期(asynchronous)」——通信の結果を待たずに画面が動き続けるという性質です。

  1. イベント発生 「文字が入力された」「ボタンが押された」「ページを下までスクロールした」などをJavaScriptが検知する。
  2. JavaScriptがHTTPリクエストを送信(非同期) 送信後も画面は固まらない。ユーザは入力やスクロールを続けられる。
  3. サーバがレスポンス(主にJSON)を返す 中身はこれまで学んだ普通のHTTPレスポンス。表現がHTMLでなくJSONなだけ。
  4. JavaScriptがDOMを書き換える 受け取ったデータをもとに、画面の必要な部分だけを更新する。

ステップ4に出てきたDOM(Document Object Model)は、 ブラウザが読み込んだHTMLをJavaScriptから操作できるようにした仕組みです。 HTMLの各タグが「オブジェクト」としてツリー状に並んでおり、 JavaScriptはそれを探して(document.querySelector)、中身を書き換えられます(textContent など)。 DOMを書き換えると、ブラウザは即座に画面へ反映します。

Ajaxは魔法ではありません。やっていることは 「URIに向かってHTTPリクエストを送り、表現(JSON)を受け取る」というWebの基本動作そのものです。 違いは、それを行うのがブラウザ本体ではなくJavaScriptで、結果の反映先がページ全体ではなくDOMの一部だ、という点だけです。

実例: 検索サジェストの裏側

検索ボックスに「とう」と打った瞬間、候補がすっと表示される——あの裏側を見てみましょう。 JavaScriptが入力を検知して、こんなHTTPリクエストを送っています。

JavaScriptが送るHTTPリクエスト(「とう」は%表記に変換されて運ばれる)

GET /api/suggest?q=%E3%81%A8%E3%81%86 HTTP/1.1
Host: www.example.com
Accept: application/json

URIの ?q=... はクエリパラメータ(検索条件などをURIに付け足す仕組み → URIのページ)。 「とう」がパーセントエンコーディングされて %E3%81%A8%E3%81%86 になっています。 サーバは候補の一覧をJSONで返します。

サーバが返すHTTPレスポンス

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "query": "とう",
  "suggestions": ["東京 天気", "豆腐 レシピ", "登山 初心者"]
}

JavaScriptはこの配列を受け取り、候補リストのDOMを書き換えます。 1文字打つごとにこの往復が繰り返されています。ページ遷移が起きないので、ユーザは入力を続けられるのです。

コードで見るAjax — fetch API

現在のAjaxの標準的な書き方がfetch APIです。 fetch(取ってくる)という名前のとおり、URIを指定してHTTPリクエストを送る関数で、 すべてのモダンブラウザに組み込まれています。 ユーザ情報を取得して画面に表示する完全な例です。

fetchでGETし、結果をDOMに反映する(async/await構文)

async function loadUser() {
  // ① URIを指定してHTTPリクエストを送り、レスポンスを待つ
  const response = await fetch("https://api.example.com/users/123", {
    headers: { "Accept": "application/json" }
  });

  // ② ステータスコードが成功(200番台)かを確認する
  if (!response.ok) {
    throw new Error("HTTPエラー: " + response.status);
  }

  // ③ レスポンスボディのJSONをJavaScriptのオブジェクトに変換する
  const user = await response.json();

  // ④ DOMを書き換えて画面に反映する
  document.querySelector("#user-name").textContent = user.name;
}

loadUser();

各行の意味を確認しましょう。

コードしていること
async function / await 「非同期処理」を待つための構文。await は通信の完了を待つが、その間もブラウザ全体は動き続ける。
fetch(URI, 設定) HTTPリクエストを送信する。メソッドを省略するとGETになる。第2引数でヘッダなどを指定できる。
response.ok ステータスコードが200〜299なら true。fetchは404や500でもエラーにならないので、自分で確認する必要がある。
response.status ステータスコードの数値(200、404など)。
response.json() レスポンスボディをJSONとして解釈し、JavaScriptのオブジェクトに変換する。
document.querySelector(...) DOMから要素を探す。"#user-name" は「idがuser-nameの要素」の意味。textContent への代入で表示が変わる。

response.ok の確認を忘れると、サーバが404(見つからない)や500(サーバ内部エラー)を返しても 処理が先へ進み、壊れたデータで画面を更新しようとして分かりにくいバグになります。 「通信できたか」と「成功したか」は別物です。必ずステータスを確認しましょう。

POSTでデータを送る — コードとHTTPメッセージの対応

取得(GET)の次は送信です。新しいユーザを登録する例で、 fetchのコードが実際にどんなHTTPメッセージになるのかを突き合わせます。 ここがこのページの肝です。

fetchでJSONをPOSTする

async function createUser() {
  const response = await fetch("https://api.example.com/users", {
    method: "POST",                                   // HTTPメソッドをPOSTに
    headers: { "Content-Type": "application/json" },  // ボディの形式を宣言
    body: JSON.stringify({                            // オブジェクトをJSON文字列に変換
      name: "佐藤花子",
      email: "hanako@example.com"
    })
  });

  if (!response.ok) {
    throw new Error("登録に失敗しました: " + response.status);
  }

  const created = await response.json();
  console.log("登録されたID:", created.id);
}

このコードを実行したとき、ネットワーク上を実際に流れるのは次のHTTPメッセージです。

実際に流れるHTTPリクエスト

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 52

{"name":"佐藤花子","email":"hanako@example.com"}

サーバが返すHTTPレスポンス(201 Created = 作成成功)

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: https://api.example.com/users/124

{"id":124,"name":"佐藤花子","email":"hanako@example.com"}

コードとメッセージの対応関係を整理します。

fetchのコードHTTPメッセージ上の姿
fetch("https://api.example.com/users", ...) リクエスト行のURI /users と Host: api.example.com
method: "POST" リクエスト行の POST
headers: { "Content-Type": ... } Content-Type: application/json ヘッダ
body: JSON.stringify({...}) 空行の下のボディ {"name":"佐藤花子",...}
response.status / response.ok ステータス行の 201 Created
response.json() レスポンスボディのJSONを解釈した結果

fetchのコードは、HTTPのページで学んだリクエストの部品 (メソッド・URI・ヘッダ・ボディ)をそのままJavaScriptの引数に写し取ったものです。 つまりfetchを理解するのに新しい知識はほぼ不要で、HTTPが分かっていれば読めます。 逆に言えば、Ajaxのトラブルはブラウザの開発者ツールで「実際に流れたHTTPメッセージ」を見れば解決できます。

XMLHttpRequestという歴史

fetchが普及する前、Ajaxの通信はXMLHttpRequest(XHR)という仕組みで書かれていました。 名前に「XML」とあるのはAjaxの名前と同じ歴史的事情です。同じGETをXHRで書くとこうなります。

かつての書き方 — XMLHttpRequest(参考)

var xhr = new XMLHttpRequest();
xhr.open("GET", "https://api.example.com/users/123");
xhr.onreadystatechange = function () {
  if (xhr.readyState === 4 && xhr.status === 200) {
    var user = JSON.parse(xhr.responseText);
    document.querySelector("#user-name").textContent = user.name;
  }
};
xhr.send();
XMLHttpRequestfetch API
登場時期 1999年ごろ(2005年のAjaxブームの立役者) 2015年ごろから標準化・普及
書き方 コールバック関数(完了時に呼ばれる関数)を登録する async/awaitで上から下へ読める
JSONの扱い JSON.parse を自分で呼ぶ response.json() が用意されている
現在の位置づけ 古いコードや記事で見かける遺産 現在の標準

XHRを紹介したのは、Web上の古い記事やコードを読むときに必ず出会うからです。 どちらも「JavaScriptからHTTPリクエストを送る」という中身は同じ。 新しく書くコードはfetch一択と覚えてください。

CORS — なぜ別ドメインへのAjaxは制限されるのか

Ajaxを試すと、かなりの確率で 「blocked by CORS policy」というエラーに出会います。正体を知っておきましょう。

ブラウザには同一オリジンポリシーという安全ルールがあります。 オリジン(origin)とは「URIのスキーム+ホスト+ポート」のこと(例: https://shop.example.jp)。 JavaScriptによるAjax通信は、原則ページ自身と同じオリジンにしか許されません。 これがないと、悪意あるサイトを開いただけで、そのページのJavaScriptがあなたのログイン済みの 別サービスへ勝手にリクエストを送り、情報を盗めてしまうからです。

とはいえ「自社サイトから自社APIサーバ(別オリジン)を呼びたい」という正当な場面は多くあります。 そこで作られたのがCORS(オリジン間リソース共有、Cross-Origin Resource Sharing)—— サーバ側が「このオリジンからなら許可する」と表明する仕組みです。ヘッダの往復を見てみましょう。

shop.example.jp のページ上のJavaScriptが api.example.com へ送るリクエスト

GET /v1/products HTTP/1.1
Host: api.example.com
Origin: https://shop.example.jp
Accept: application/json

サーバの許可付きレスポンス

HTTP/1.1 200 OK
Content-Type: application/json
Access-Control-Allow-Origin: https://shop.example.jp

[{"id": 1, "name": "コーヒー豆 200g"}]
  1. ブラウザが Origin ヘッダを自動で付ける 「このリクエストは https://shop.example.jp のページから発生しました」という申告。JavaScriptからは偽装できない。
  2. サーバが Access-Control-Allow-Origin で応答する 「そのオリジンからのアクセスを許可します」という表明。
  3. ブラウザが照合し、許可がなければJavaScriptに結果を渡さない このときコンソールに出るのが「blocked by CORS policy」エラー。

CORSエラーは「通信の故障」ではなく、サーバが許可を表明していないことをブラウザが検知した状態です。 直す場所はJavaScript側ではなく、サーバ側の設定(許可ヘッダを返すこと)が基本です。 なお、データを書き換えるようなリクエストでは、ブラウザが本番の前にOPTIONSメソッドで 「送ってもよいか」を確認するプリフライトリクエストという事前確認も行われます。

SPAへ — 現在のWebアプリの構図

Ajaxの徹底がSPAを生みました。 一部だけの更新を突き詰め、最初の1回だけHTMLとJavaScriptを受け取り、 以後の画面遷移をすべてJavaScriptが担う方式を SPA(シングルページアプリケーション)と呼びます。サーバとの会話は「Web API + JSON」だけになり、 ReactやVueなどのフレームワークが「JSONの変化に合わせてDOMを効率よく書き換える」部分を引き受けています。 Webメールや業務システムなど、現在の「アプリらしいWeb」はほぼこの構図です。

SSRとハイドレーション。 SPAは初回表示が遅くなりがちなので、最初のHTMLはサーバ側で組み立てて返し(SSR、サーバサイドレンダリング)、 その後にJavaScriptが引き継ぐ「ハイドレーション」という折衷も一般化しています。

サーバから送る通信も。 HTTPはクライアントから始まるのが原則ですが、 チャットや通知のように「サーバから知らせたい」場面のために、 WebSocket(双方向の常時接続)やSSE(Server-Sent Events、サーバからの逐次送信)という仕組みも使われています。 これらはAjaxの補完であり、日常のデータ取得・送信は今もHTTP + JSONが主役です。

ここまでで「JavaScriptがWeb APIを呼ぶ」側の仕組みが分かりました。 次のページでは視点をサーバ側に移し、呼ばれるWeb APIをどう設計するか (URIの付け方、メソッドとステータスコードの選び方)を学びます。
