用語集

全体・基盤

Web(World Wide Web)
インターネット上で動く情報システム。文書などの情報(リソース)をハイパーリンクで相互につなぎ、公開・閲覧できるようにした仕組み。1990年ごろにティム・バーナーズ=リーが考案した。→ Webとは
インターネット(the Internet)
世界中のネットワーク同士を相互接続した通信網そのもの。Webはその上で動くサービスのひとつであり、両者は別物。→ Webとは
TCP/IP
インターネットの基盤となる通信プロトコルの一族。データを小さな単位に分けて相手のコンピュータまで確実に届ける役割を担い、HTTPはこの上に乗って動く。→ HTTP
DNS(Domain Name System)
ドメイン名(例: example.com)を、ネットワーク上の実際の住所であるIPアドレスに変換する仕組み。「インターネットの電話帳」にたとえられる。→ 全体像
IPアドレス(IP address)
ネットワーク上のコンピュータ1台1台を識別する番号。人間には覚えにくいため、普段はドメイン名を使い、DNSで変換する。
クライアント/サーバ(client/server)
Web通信の役割分担。依頼する側(ブラウザやアプリ)がクライアント、依頼を受けて応答する側がサーバ。やりとりは常にクライアント側から始まる。→ Webとは
プロトコル(protocol)
通信の手順やデータ形式の取り決め。双方が同じプロトコルに従うことで、メーカーやOSが違うコンピュータ同士でも会話できる。HTTPやTCP/IPはいずれもプロトコル。
RFC(Request for Comments)
IETFが発行するインターネット標準の仕様書。番号で管理され、誰でも無料で読める。例: URIはRFC 3986、HTTPはRFC 9110で定義。→ Webとは
標準化(IETF/WHATWG/W3C)
Webの仕様をオープンに決める活動と、その担い手の団体。IETFは基盤プロトコル(HTTP・URIなど)、WHATWGはHTMLやブラウザ関連仕様、W3CはCSSなどのWeb技術を担当する。→ Webとは

識別(URI)

リソース(resource)
Web上の「名前を付けて指し示せる情報」。ユーザのプロフィール、商品の在庫、今日の天気など。リソースにはURIで名前を付け、実際にやりとりするのはその「表現」。→ URI / REST
URI(Uniform Resource Identifier)
リソースを世界中で一意に識別するための「住所」の書式。RFC 3986で定義。Webのハイパーリンクの行き先はすべてURIで指定される。→ URI
URL(Uniform Resource Locator)
URIのうち、リソースの「場所」で識別するもの。日常で目にするWebのアドレスはほぼすべてURL。厳密にはURIの一種だが、実用上はほぼ同義に使われる。→ URI
URN(Uniform Resource Name)
URIのうち、場所ではなく「名前」で識別するもの。例: 書籍のISBNを表す urn:isbn:...。場所が変わっても識別子が変わらないのが特徴。→ URI
スキーム(scheme)
URIの先頭部分で、リソースへのアクセス手段を示すもの。https://... の https がスキーム。他に http、mailto など。→ URI
クエリパラメータ(query parameter)
URIの ? 以降に付ける「名前=値」形式の追加情報。検索条件や並び替えの指定に使う。例: /books?q=web&sort=year。→ URI / API設計
%エンコーディング(percent-encoding)
URIに使えない文字(日本語や空白など)を %XX 形式で表す変換ルール。例: 「あ」は %E3%81%82。→ URI
クールURI(Cool URIs)
「クールなURIは変わらない」という設計指針。一度公開したURIを変えない・壊さないことで、リンク切れを防ぎ、Webの信頼性を保つ。API設計にも適用される。→ URI / API設計

転送(HTTP)

HTTP(Hypertext Transfer Protocol)
URIで示されたリソースとその表現をやりとりするための通信プロトコル。Webの「配送手順」にあたる。現行仕様はRFC 9110などで定義。→ HTTP
HTTPS
TLSで暗号化された上でやりとりされるHTTP。盗聴・改ざん・なりすましを防ぐ。現在のWebでは原則としてHTTPSが必須。→ HTTP
TLS(Transport Layer Security)
通信を暗号化し、相手が本物であることを証明書で確認するプロトコル。HTTPSの「S」を支える土台。→ HTTP
リクエスト/レスポンス(request/response)
HTTP通信の基本単位。クライアントが依頼文(リクエスト)を送り、サーバが結果(レスポンス)を返す1往復。Webのすべてはこの繰り返しでできている。→ HTTP
HTTPメソッド(HTTP method)
リクエストの先頭で示す「操作の種類」。GET/POST/PUT/DELETEなど少数に限定されており、これが統一インターフェースを支える。→ HTTP
GET
リソースの取得を表すメソッド。リソースの状態を変えない「安全」なメソッドで、結果をキャッシュできる。→ HTTP
POST
リソースの新規作成や、その他の処理の依頼を表すメソッド。同じリクエストを繰り返すと結果が変わりうる(冪等でない)点に注意。→ HTTP
PUT
リソースを送った内容で置き換える(更新・作成する)メソッド。何度繰り返しても結果が同じ(冪等)。→ HTTP
DELETE
リソースの削除を表すメソッド。これも冪等で、何度実行しても「そのリソースが無い」状態に落ち着く。→ HTTP
ステータスコード(status code)
レスポンスの先頭で結果の種類を表す3桁の数字。200(成功)、201(作成)、404(見つからない)、500(サーバエラー)など。百の位が大分類を表す。→ HTTP
ヘッダ(header)
リクエストやレスポンスに付ける「名前: 値」形式のメタ情報。中身の形式(Content-Type)、キャッシュの指示、認証情報などを運ぶ。→ HTTP
MIMEタイプ(Content-Type)
データの種類を表す「大分類/小分類」形式のラベル。例: text/html、application/json。レスポンスではContent-Typeヘッダで伝えられ、受け手はこれを見て解釈方法を決める。→ HTTP
ステートレス(stateless)
サーバがクライアントの状態(前回のやりとり)を覚えず、毎回のリクエストに必要な情報をすべて含めさせる方式。サーバを増やしやすくなり、Webの拡張性の要となっている。→ HTTP / REST
Cookie(クッキー)
サーバがブラウザに保存させる小さなデータ。次回以降のリクエストに自動で添付され、ステートレスなHTTPの上でログイン状態などを実現するために使われる。→ HTTP
セッション(session)
ログインからログアウトまでのような「一連のやりとり」のまとまり。ステートレスなHTTPでは、Cookieなどに載せた識別子でセッションを表現する。→ HTTP
キャッシュ(cache)
一度取得したレスポンスを保存して再利用する仕組み。通信を減らして表示を速くし、サーバの負荷を下げる。Cache-ControlヘッダなどでHTTPに組み込まれている。→ HTTP
ETag(エンティティタグ)
リソースの版(バージョン)を表す識別子のヘッダ。クライアントが「手元の版はこれ」と伝え、変わっていなければサーバは中身を送らずに済む(条件付きリクエスト)。→ HTTP
冪等性(べきとうせい、idempotence)
同じ操作を何度繰り返しても結果が同じになる性質。GET・PUT・DELETEは冪等、POSTは冪等でない。通信失敗時に安心して再送できるかどうかの判断基準になる。→ HTTP
安全性(safety)
その操作がリソースの状態を変えない性質。GETは安全なメソッドであり、だからこそ検索エンジンの巡回やキャッシュが成り立つ。→ HTTP
HTTP/2
2015年に標準化されたHTTPの新しい版。1つの接続で複数のやりとりを並行して運べるようにし、高速化した。メソッドやステータスコードの意味は変わらない。→ HTTP
HTTP/3
2022年に標準化された最新版。土台の通信方式をTCPからQUIC(UDPベース)に替えてさらに高速化した。これも「意味の部分」はHTTP/1.1から不変。→ HTTP
持続的接続 / keep-alive
1本のTCP接続を開いたまま、複数のリクエスト/レスポンスを続けてやりとりする方式。接続の開け閉めを減らして高速化する。HTTP/1.1で既定になった。→ HTTP:持続的接続
パイプライン(pipelining)
1本の接続で、前のレスポンスを待たずにリクエストを連続送信する仕組み。ただしレスポンスは送信順に返す必要があり(先頭詰まり)、実装も不安定なため、ブラウザでは事実上使われない。→ HTTP:持続的接続
多重化(multiplexing)
1本の接続の中で、多数のリクエスト/レスポンスを順不同で同時にやりとりする方式。HTTP/2で導入され、パイプラインの「先頭詰まり」を解消した。HTTP/1.1が複数接続で並列化していたのを1接続に統合した形。→ HTTP:持続的接続
Content-Disposition
ボディを画面に表示(inline)するか、ファイルとして保存(attachment)させるかを指示するレスポンスヘッダ。保存名も指定でき、日本語名は filename*=UTF-8''… の%エンコーディングで正しく渡す。→ HTTP:ヘッダ
プロキシ(proxy)
クライアントとサーバの通信を中継する機器。HTTPを理解して動くアプリケーション層の中継役で、リクエストを代理で送ったり、応答をキャッシュしたりする。エラー時は自分でHTTP応答を生成して返すことがある。→ 経路とエラー
フォワードプロキシ / リバースプロキシ
フォワードプロキシはクライアント側に立ち、組織の「外部への出口」としてアクセス制御(ACL)やログ取得を担う(例: Squid)。リバースプロキシはサーバ側に立ち、複数のサーバへの振り分けや負荷分散を担う。→ 経路とエラー
ゲートウェイ(gateway)
目的のサーバの手前で受け付け、上流(本当のサーバ)に取り次ぐ中継役。上流に届かなければ、自分で 502 や 504 を返す。→ 経路とエラー
ファイアウォール / パケットフィルタ
通信を通す・通さないを判断する防御機器。基本はIPアドレスやポートを見るネットワーク層(L3/L4)の機器で、HTTPの中身は見ない。遮断は「黙って破棄(DROP)→タイムアウト」か「RSTで拒否(REJECT)→即座に接続拒否」で、HTTPコードは出さないのが原則。→ 経路とエラー
403 Forbidden
「理解したが、認可を拒否する」ことを表す4xx(クライアントエラー)。認証をやり直しても解決しない点が401と違う。プロキシがACLでアクセスを拒否したときの標準的な応答でもある。→ 経路とエラー
502 / 503 / 504(ゲートウェイ系のエラー)
いずれも5xx(サーバ側の失敗)。502=上流から不正な応答、503=一時的に応答できない(過負荷・メンテ、ブロックの合図にも流用される)、504=上流が時間内に応答しない(タイムアウト)。中継装置が「上流に届かなかった/提供できない」ときに返す。→ 経路とエラー
ping / ICMP
相手ホストまでパケットが往復できるか(L3の到達性)を確かめる基本ツールと、その土台のプロトコル。「届くか」の最初の目安。ただしICMPだけ遮断されることもあり、ping不通=障害とは限らない。→ CLI診断
traceroute / tracert
相手までの経路(通過する中継点=ホップ)を順にたどり、どこで止まるかを見るツール。Linuxは traceroute、Windowsは tracert。→ CLI診断
Test-NetConnection(PowerShell)
Windowsの多機能な疎通確認コマンド。-Port で特定ポートにTCP接続できるか(L4)、-TraceRoute で経路を確認できる。Test-Connection はICMP ping相当。→ CLI診断
ss / netstat
今つながっている/待ち受けているTCP・UDPの接続一覧を表示するツール(L4)。どのポートが開いているか、どこと通信中かが分かる。→ CLI診断
Invoke-WebRequest / Invoke-RestMethod(PowerShell)
PowerShellでHTTPリクエストを送るコマンド。前者はステータス・ヘッダ・本文を持つ応答を返し、後者はJSONを自動でオブジェクトに変換する。curl / wget のWindows版にあたる。→ CLI診断
openssl s_client
TLSハンドシェイクを実際に行い、サーバ証明書の中身(発行者・有効期限・対象ドメイン)やプロトコル版を確認するツール(TLS層)。→ CLI診断
パケットキャプチャ(tcpdump / pktmon / Wireshark)
ネットワークを流れる生のパケットを捕まえて記録し、後から中身を解析する上級ツール。他のツールで切り分かないときの最終手段。→ CLI診断

表現(フォーマット)

HTML(HyperText Markup Language)
Webページの中身を記述するマークアップ言語で、人間向けの代表的な「表現」。リンクを埋め込めるためハイパーメディアを実現できる。仕様はWHATWGのHTML Living Standard。→ HTML
タグ(tag)
HTMLで文書に意味を付ける印。<h1>(見出し)や <a>(リンク)のように、山かっこで要素を挟んで使う。→ HTML
マークアップ(markup)
文章に「ここは見出し」「ここはリンク」といった構造の印を付けていくこと。HTMLはマークアップのための言語。→ HTML
セマンティックHTML(semantic HTML)
見た目ではなく「意味」に基づいてタグを選ぶ書き方。検索エンジンや読み上げソフトなど、プログラムにも文書の構造が伝わるようになる。→ HTML
CSS(Cascading Style Sheets)
HTMLの「見た目」(色・配置・文字サイズなど)を指定する言語。構造(HTML)と見た目(CSS)を分けるのが現在の標準的な作法。→ HTML
JavaScript
ブラウザ上で動くプログラミング言語。ページの書き換えやWeb APIの呼び出しなど、Webに「動き」を与える。RESTの制約「コードオンデマンド」の実例でもある。→ Ajax
DOM(Document Object Model)
ブラウザが読み込んだHTMLを、JavaScriptから操作できるようにした木構造のデータ。DOMを書き換えると画面の表示が変わる。→ Ajax
XML(Extensible Markup Language)
データ交換用の汎用マークアップ言語。書籍刊行の2010年ごろはWeb APIの表現の有力候補だったが、現在はより軽量なJSONが主流。→ HTML
JSON(JavaScript Object Notation)
「名前と値の組」でデータを表す軽量なデータ形式。RFC 8259で定義。現在のWeb APIにおけるプログラム向けの表現の事実上の標準。→ HTML / API設計
ハイパーメディア(hypermedia)
文書・画像などの情報をリンクで相互につないだシステム。読者はリンクをたどって情報から情報へ自由に移動できる。Webの本質のひとつ。→ Webとは
ハイパーリンク(hyperlink)
ある情報から別の情報への参照。HTMLでは <a href="..."> で表し、行き先はURIで指定する。単に「リンク」とも。→ HTML
microformats(マイクロフォーマット)
独立した新形式ではなく、既存HTMLの class 属性に決まった名前を付けて機械可読な意味を埋め込む規約(例: h-card)。「人間と機械が同じ文書を読む」狙い。現在は同じ目的がJSON-LD/schema.orgに継承。→ HTML:フォーマット総覧
Atom
ブログやニュースの更新一覧(フィード)を表すXMLベースの標準フォーマット(RFC 4287)。feed の中に entry が並び、各項目が更新日時・著者・リンクなどのメタデータを持つ。RSSを整理・一般化した後継。→ HTML:フォーマット総覧
Atom Publishing Protocol(AtomPub)
フォーマットではなくプロトコル。Atom文書を表現に使い、HTTPのメソッド(GET/POST/PUT/DELETE)でリソースをCRUD操作する手順を定めた(RFC 5023)。REST的なAPIの先駆で、発想は現代のREST+JSON APIに継承。→ HTML:フォーマット総覧 / REST

設計思想(REST/API)

REST(REpresentational State Transfer)
Roy Fieldingが2000年の博士論文で整理した、Webの設計原則(アーキテクチャスタイル)。6つの制約の組み合わせとして定義され、名前は「表現による状態の転送」を意味する。→ REST
RESTful(レストフル)
「RESTの原則に沿っている」ことを表す形容詞。リソースにURIを付け、統一インターフェースで操作する設計になっているAPIを「RESTfulなAPI」と呼ぶ。→ REST
アーキテクチャスタイル(architectural style)
個別のシステムではなく、設計の「型・様式」のこと。建築における和風・洋風のような様式にあたる。RESTはWebというシステム群のアーキテクチャスタイル。→ REST
統一インターフェース(uniform interface)
限られた共通のメソッド(GET/POST/PUT/DELETEなど)だけで、あらゆるリソースを同じ作法で操作するというRESTの中心的な制約。初見のAPIでも操作を推測できる根拠。→ REST
CRUD(クラッド)
データ管理の4つの基本操作 Create(作成)/Read(読み取り)/Update(更新)/Delete(削除)の頭文字。HTTPメソッドのPOST/GET/PUT/DELETEときれいに対応する。→ REST
エンドポイント(endpoint)
APIの窓口となる個々のURI(とメソッドの組)。例: GET /books/42。エンドポイントの一覧がAPI仕様の骨格になる。→ API設計
Web API
プログラム同士がHTTPでデータをやりとりするための窓口。人間向けのWebサイトと同じ仕組み(URI+HTTP+表現)を、JSONなどのプログラム向け表現で使うもの。→ 全体像 / API設計
HATEOAS
Hypermedia As The Engine Of Application State の略。レスポンスの中に「次に辿れるリンク」を含め、クライアントがリンクを辿って操作を進められるようにする設計。REST成熟度モデルの最上位レベル。→ REST
成熟度モデル(Richardson Maturity Model)
APIが「どこまでRESTの原則に従っているか」をレベル0〜3で測る物差し。実務ではレベル2(メソッドとステータスコードの正しい使い分け)が事実上の標準。→ REST
バージョニング(versioning)
APIの版数を管理し、新旧仕様を並行運用できるようにすること。URIに /v1/ を入れる方式が主流。→ API設計
ページネーション(pagination)
一覧系APIで、大量の結果を「1ページ分ずつ」小分けにして返す仕組み。page/per_page や limit/offset といったクエリパラメータで指定する。→ API設計
OpenAPI
APIの仕様書を機械可読(YAML/JSON)に書くための標準。旧称Swagger。ドキュメント自動生成・コード生成・モック作成の起点として現在の実務で広く使われる。→ API設計
GraphQL
クライアントがクエリ(問い合わせ文)を書き、必要なデータだけをまとめて取得できるAPIスタイル。RESTとは別のアプローチだが、HTTPの上で動く点は同じ。→ REST
gRPC
関数呼び出しのように相手サーバの処理を呼ぶ、高速なバイナリ通信の仕組み。データセンター内部のサービス間通信で使われることが多い。→ REST / RPC/SOAP

手続き呼び出し(RPC/SOAP)

RPC(Remote Procedure Call、遠隔手続き呼び出し)
手元の関数呼び出し getUser(123) のように、遠くのサーバの処理を呼び出す発想。RESTが「名詞(リソース)」中心なのに対し、RPCは「動詞(手続き)」中心。→ RPC/SOAP
XML-RPC
1998年登場の最小のHTTP-RPC。命令名と引数をXMLで書き、1つのURIへHTTP POSTで送る。失敗してもHTTPは200のままで、詳細はボディの fault で伝える。→ RPC/SOAP
SOAP
1998〜2000年に登場したXMLメッセージング仕様。メッセージを Envelope(封筒)で包み、Header(メタデータ)と Body(本文)に分ける。企業システム向けの重装備。当初は略語だったがSOAP 1.2以降は固有名詞。→ RPC/SOAP
SOAP Envelope / Fault
Envelopeはメッセージ全体を包む一番外側の要素。Faultは失敗時にBody内へ入れる障害情報で、SOAPはHTTPの404等を使わずFaultの中身で意味を伝える。→ RPC/SOAP
WSDL(Web Services Description Language)
SOAPサービスが「どんな操作を・どんな引数で・どんな戻り値で」提供するかを機械可読なXMLで定義した仕様書。クライアントのコードを自動生成できる。→ RPC/SOAP
トンネリング(tunneling)
あるプロトコルを別のプロトコルの中に包んで通すこと。SOAP/XML-RPCはHTTP POSTの中にXMLメッセージを入れて運ぶ「HTTPトンネリング」を行う。HTTPは中身を解釈せず運ぶだけになる。→ RPC/SOAP
JSON-RPC
XML-RPCの発想をJSONで行う軽量なRPC仕様。XMLの代わりにJSONで命令名と引数を送る。RPCの発想の現代的な後継の一つ。→ RPC/SOAP

ブラウザ・動的なWeb

Ajax(エイジャックス、Asynchronous JavaScript + XML)
JavaScriptがページを再読み込みせずにHTTP通信を行い、画面の一部だけを更新する技法。2005年ごろのGoogle マップで広く知られた。名前にXMLとあるが現在のやりとりはほぼJSON。→ Ajax
fetch API
JavaScriptからHTTPリクエストを送るための現在標準の機能。fetch(url) と書くだけでWeb APIを呼び出せる。旧来のXMLHttpRequestを置き換えた。→ Ajax
XMLHttpRequest
fetch API以前に使われていた、JavaScriptからHTTP通信を行うための機能。Ajaxという言葉が生まれた当時の主役で、現在は主に古いコードで見かける。→ Ajax
非同期通信(asynchronous communication)
通信の完了を待たずに他の処理を進め、結果が届いたら続きを実行するやり方。画面が固まらないWebアプリの基本であり、Ajaxの「A」にあたる。→ Ajax
SPA(Single Page Application)
最初に1枚のHTMLとJavaScriptを読み込み、以降はJavaScriptがWeb APIを呼んで画面を書き換え続けるWebアプリの形。「サイトとしてのWeb」と「APIとしてのWeb」が1つのサービス内で同時に動く。→ Ajax
CORS(Cross-Origin Resource Sharing)
ブラウザ上のJavaScriptが「別のオリジン」のAPIを呼ぶことを、サーバ側の許可に基づいて安全に認める仕組み。許可がなければブラウザが通信結果の利用を遮断する。→ Ajax
オリジン(origin)
スキーム+ホスト名+ポート番号の組で表される「サイトの出どころ」。例: https://example.com。ブラウザのセキュリティはオリジン単位で区切られている。→ Ajax
WebSocket
クライアントとサーバが接続をつなぎっぱなしにして、双方向にデータを送り合えるプロトコル。チャットや通知など「サーバ側から話しかけたい」場面で使う。リクエスト/レスポンス型のHTTPを補う存在。→ Ajax
開発者ツール(DevTools)
ブラウザに内蔵された調査用の道具箱。F12で開き、HTML構造・CSS・JavaScript・HTTP通信などをサーバに触れず観察できる。Edge も Chrome も同じ Chromium 系で共通。→ DevTools
Networkパネル
DevToolsの中で、発生したHTTPリクエスト/レスポンスを一覧・詳細表示するパネル。ステータス・ヘッダ・ボディ・所要時間が見え、curl -v のGUI版にあたる。→ DevTools
Elementsパネル / DOM
Elementsパネルは、ブラウザが組み立てた描画後のHTML構造(DOM)と適用中のCSSを見るパネル。生のHTMLではなく、JavaScriptの変更も反映した「今の構造」を表す。→ DevTools

このカテゴリの用語(fetch API、SPA、CORS、WebSocketなど)や、設計思想カテゴリのOpenAPI・GraphQL・gRPC、 転送カテゴリのHTTP/2・HTTP/3は、いずれも書籍『Webを支える技術』(2010年)の刊行後に登場・定着した用語です。 新しい用語が増えても、それらはすべて「識別=URI・転送=HTTP・表現=フォーマット・設計思想=REST」という 本サイトの地図のどこかに収まります。新語に出会ったら、まず「どの層の話か」を考えてみてください。
