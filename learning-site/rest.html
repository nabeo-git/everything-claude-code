REST — Webの設計思想

URI・HTTP・HTMLは、ダウンロードしたり実装したりできる「実物のある技術」でした。 このページで学ぶRESTだけは性質が違います。RESTは技術そのものではなく、 「それらをどう組み合わせると良いシステムになるか」という設計の考え方です。 Web APIの世界で「REST API」「RESTful」という言葉が飛び交う理由も、ここを押さえるとすっきり分かります。 書籍『Webを支える技術』第1部(第3章)と、本全体を貫くテーマに対応する、本サイトの要のページです。

RESTは「モノ」ではなく「考え方」

HTTPには仕様書があり、HTMLはファイルとして保存できます。しかしRESTは、 ダウンロードもインストールもできません。RESTとは、Roy Fielding(ロイ・フィールディング)が 2000年の博士論文で発表した、Webの設計原則の整理だからです。 Fieldingは、爆発的に成功しつつあったWebを観察し、「なぜWebはこれほどうまくいっているのか」を 理論としてまとめました。それがRESTです。

RESTのような「考え方」を、専門用語でアーキテクチャスタイル(architectural style、設計の型・様式)と呼びます。

建築の世界には「和風建築」「洋風建築」といった様式があります。 様式は特定の家そのものではなく、「屋根はこう作る」「柱はこう配置する」という設計の方針の集まりです。 同じ和風建築でも、建つ家は一軒一軒違いますね。 RESTも同じで、RESTという様式に沿って設計された個別のシステム(家)が、世界中のWebサービスやWeb APIなのです。

順序に注意してください。RESTが先にあってWebが作られたのではなく、 先に成功したWebがあり、その成功の理由を後から理論化したものがRESTです(→ Webとはのページ)。 だからRESTを学ぶことは「Webがうまくいっている理由」を学ぶことと同じです。

リソース指向 — RESTの名前の意味

RESTの世界では、Web上のあらゆる情報をリソース(resource)と捉えます。 ユーザのプロフィール、今日の天気、商品の在庫、ブログ記事——「名前を付けて指し示せる情報」はすべてリソースです。 そして次の2つを組み合わせて扱います。

  1. リソースにURIで名前を付ける 例: ユーザ123というリソースに https://api.example.com/users/123 という世界で一意な住所を与える。→ URIのページ
  2. リソースの「表現」をやりとりする リソースそのものは概念なので、ネットワーク上を流れるのはその表現(representation)——具体的にはHTMLやJSONなどのデータ。→ HTMLのページ

ここでRESTという名前の意味が分かります。RESTは REpresentational State Transfer の略で、 直訳すると「表現による状態の転送」。 「リソースの状態(いまの中身)を、表現(HTMLやJSON)という形にして、クライアントとサーバの間で転送し合う」—— Webのやりとりの本質を、そのまま名前にしたものです。

同じリソースが複数の表現を持てる点も重要です。同じユーザ123でも、 ブラウザにはHTML、プログラムにはJSONを返せます(→ 全体像ページの実例)。 「リソース(概念)」と「表現(実際のデータ)」の区別は、書籍『Webを支える技術』でも繰り返し強調される考え方です。

RESTを構成する6つの制約

Fieldingは、RESTを6つの制約(constraint、設計上の縛り)の組み合わせとして定義しました。 「縛り」と聞くと窮屈そうですが、逆です。全員が同じ縛りを守るからこそ、 世界中のバラバラなコンピュータが協調できます。

制約どういうことかそれで何が嬉しいか
クライアント/サーバ 画面(クライアント)とデータ処理(サーバ)の役割を分離する。 それぞれ独立に開発・改良できる。同じサーバをブラウザ・スマホアプリ・他のプログラムが共有できる。
ステートレス サーバはクライアントの状態を覚えず、毎回のリクエストに必要な情報をすべて含める(→ HTTPのページ)。 サーバを何台にも増やせる(どのサーバが受けても同じ)。障害からの復帰も簡単。
キャッシュ 一度取得したレスポンスを、クライアントや中継サーバが再利用してよい。 通信が減って速くなる。サーバの負荷が下がる。
統一インターフェース すべてのリソースを、限られた共通のメソッドだけで操作する(次のセクションで詳述)。 初めて見るAPIでも操作方法を推測できる。ブラウザや中継機器が「意味」を理解して協調できる。
階層化システム クライアントとサーバの間に、プロキシ(中継サーバ)やロードバランサ(負荷分散装置)を挟んでよい。 キャッシュや負荷分散を後付けできる。クライアントは相手が本物のサーバか中継かを気にしなくてよい。
コードオンデマンド(任意) サーバからプログラムコード(現在は主にJavaScript)を送り、クライアント側で実行できる。 クライアントの機能を後から拡張できる。6つの中で唯一「採用してもしなくてもよい」制約。

6つの制約をすべて(コードオンデマンドは任意で)満たすアーキテクチャスタイルがRESTです。 どれも派手な発明ではなく、「分離する」「覚えない」「共通化する」という地味な約束事の積み重ねである点に注目してください。

統一インターフェース — RESTの心臓部

6つの制約の中で最もRESTらしいのが統一インターフェース(uniform interface)です。 意味は「限られたメソッド(GET/POST/PUT/DELETEなど)だけを使い、あらゆるリソースを同じ作法で操作する」こと。 リソースごとに独自の命令を発明するのではなく、どのリソースに対しても 「取得はGET、作成はPOST、更新はPUT、削除はDELETE」という共通の型で通します。

この4操作は、データ管理の基本操作CRUD(クラッド: Create/Read/Update/Delete)ときれいに対応します。

CRUD意味HTTPメソッドユーザ管理APIでの例
Create作成POST(または PUT)POST /users — ユーザを新規作成
Read読み取りGETGET /users/123 — ユーザ123を取得
Update更新PUTPUT /users/123 — ユーザ123を書き換え
Delete削除DELETEDELETE /users/123 — ユーザ123を削除

操作の種類をむやみに増やさない——この不自由さこそがRESTの強さです。 メソッドの意味が世界共通だから、初めて見るAPIでも「一覧はたぶん GET /users だろう」と推測でき、 ブラウザ・プロキシ・検索エンジンといった第三者のソフトウェアも「GETなら安全に読めるはず」と判断して協調できます。 各メソッドの正確な性質(安全性・冪等性)は HTTPのページで扱っています。

REST APIの実例 — ユーザ管理APIの5往復

理屈がそろったので、実物を見ましょう。架空のユーザ管理API(api.example.com)に対する 基本の5往復です。URIがリソースを指し、メソッドが操作を表し、JSONが表現として流れる—— ここまでの話がすべて詰まっています。

① 一覧の取得 — GET /users

リクエスト

GET /users HTTP/1.1
Host: api.example.com
Accept: application/json

レスポンス(200 OK)

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "users": [
    { "id": 101, "name": "田中太郎" },
    { "id": 123, "name": "佐藤花子" }
  ]
}

② 個別の取得 — GET /users/123

リクエスト

GET /users/123 HTTP/1.1
Host: api.example.com
Accept: application/json

レスポンス(200 OK)

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "id": 123,
  "name": "佐藤花子",
  "email": "hanako@example.com",
  "joined": "2024-04-01"
}

③ 作成 — POST /users

作成に成功すると、ステータスコード 201 Created と、 新しく生まれたリソースのURIを示す Location ヘッダが返ります。

リクエスト(ボディに作成内容)

POST /users HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "鈴木一郎",
  "email": "ichiro@example.com"
}

レスポンス(201 Created + Location)

HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: https://api.example.com/users/124

{
  "id": 124,
  "name": "鈴木一郎",
  "email": "ichiro@example.com",
  "joined": "2026-07-19"
}

④ 更新 — PUT /users/124

リクエスト(新しい内容で置き換え)

PUT /users/124 HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "name": "鈴木一郎",
  "email": "ichiro-new@example.com"
}

レスポンス(200 OK)

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{
  "id": 124,
  "name": "鈴木一郎",
  "email": "ichiro-new@example.com",
  "joined": "2026-07-19"
}

⑤ 削除 — DELETE /users/124

削除に成功すると、「成功したが返す中身はない」を意味する 204 No Content が返ります(ボディは空)。

リクエスト

DELETE /users/124 HTTP/1.1
Host: api.example.com

レスポンス(204 No Content)

HTTP/1.1 204 No Content

エラーのとき — 404 Not Found

存在しないリソースを指定すると、エラーもまた統一された作法(ステータスコード)で返ります。

リクエスト(存在しないID)

GET /users/999 HTTP/1.1
Host: api.example.com
Accept: application/json

レスポンス(404 Not Found)

HTTP/1.1 404 Not Found
Content-Type: application/json; charset=utf-8

{
  "error": "user_not_found",
  "message": "ID 999 のユーザは存在しません"
}

5往復すべてで、URI(名詞)は同じ形、操作の違いはメソッド(動詞)だけ、結果はステータスコードで表現されています。 この規則正しさがREST APIの読みやすさの正体です。 ステータスコードの体系は HTTPのページ、URIの設計指針は API設計のページで詳しく扱います。

RESTfulとは・REST成熟度モデル

RESTful(レストフル)とは、「RESTの原則に沿っている」ことを表す形容詞です。 「RESTfulなAPI」と言えば、リソースにURIを付け、統一インターフェースで操作する設計になっているAPI、という意味です。 ただし現実のAPIには「どこまでRESTの原則に従っているか」の程度差があります。 その度合いを測る物差しとして有名なのが、Leonard Richardson(レナード・リチャードソン)の成熟度モデルです。

レベル特徴ようすの例
レベル0 HTTPをただの通り道として使う。1つのURIに何でもPOSTで送る。 POST /api にボディで「getUserしてください」と書く。
レベル1 リソースごとにURIを分ける。 /users/123 や /orders/7 が登場する。ただし操作はまだ何でもPOST。
レベル2 HTTPメソッドとステータスコードを正しく使い分ける。現実の多くの「REST API」はここ。 GET /users/123 が200、作成は POST で201、失敗は404や400。
レベル3 HATEOAS — レスポンスに「次に辿れるリンク」を含める。 ユーザ情報の中に、注文一覧へのリンクが入っている(下の例)。

レベル3のHATEOAS(Hypermedia As The Engine Of Application State)は、 「レスポンス自身が次に進める先のリンクを教えてくれる」仕組みです。 ハイパーリンクを辿って進むWebサイトの体験(→ HTMLのページ)を、APIの世界でも実現しようという発想です。

HATEOAS形式のレスポンスの例(リンクを含むJSON)

{
  "id": 123,
  "name": "佐藤花子",
  "_links": {
    "self":   { "href": "/users/123" },
    "orders": { "href": "/users/123/orders" },
    "posts":  { "href": "/users/123/posts" }
  }
}

実務では、HATEOASまで実装するAPIは少数派で、レベル2が事実上の標準です。 「REST API」と名乗るAPIのほとんどは「リソースのURI + メソッドとステータスコードの正しい使い分け」を指している、 と理解しておくと現場の会話とずれません。

なぜRESTだとうまくいくのか

制約を守ると何が起きるのか、効果の面からまとめ直します。

初見でも推測が効く

統一インターフェースのおかげで、初めて使うAPIでも「一覧は GET /xxx、作成は POST /xxx」と当たりを付けられる。学習コストが激減する。

サーバを並べられる

ステートレスだから、リクエストをどのサーバが処理しても同じ。アクセスが増えたらサーバを足すだけでよい。

キャッシュが効く

「GETは安全に再利用できる」と決まっているから、結果を保存して使い回せる。速くて安いWebの土台。

既存インフラに乗れる

階層化システムのおかげで、CDN(世界中に配置されたキャッシュ網)やプロキシなど、Webのために整備済みのインフラをそのまま利用できる。

ひとことで言えば、RESTに従うことは「Webがうまくいった理由の再利用」です。 Webサイトを30年支えてきた仕組み(URI・HTTP・キャッシュ・リンク)にAPIも乗せてしまえば、 同じスケーラビリティ(拡張性)と安定性が手に入る——これがREST APIが世界標準になった理由です。

最新動向: RESTと他スタイルの比較

書籍刊行(2010年)後、REST以外のAPIスタイルも実用化されました。それぞれ得意分野が違います。

スタイルひとことで言うと得意分野・使い所
REST(+ JSON) リソースをURIとHTTPメソッドで操作する 公開Web API全般。シンプルでキャッシュが効き、HTTPの道具がそのまま使える。
GraphQL クライアントがクエリ(問い合わせ文)を書き、必要なデータだけをまとめて取る 画面ごとに必要なデータの形が違うアプリ。取得の過不足(取りすぎ・往復しすぎ)を減らしたいとき。
gRPC 関数呼び出しのように相手のサーバの処理を呼ぶ、高速なバイナリ通信 データセンター内部のサービス間(マイクロサービス)の高速通信。人間が直接読む用途には不向き。
RPCスタイル 「命令名+引数」を送る古典的な形(成熟度モデルのレベル0に相当) 操作が「リソースの取得・更新」に整理しづらい、手続き中心の社内APIなど。

使い分けが進んだ現在でも、不特定多数に公開するWeb APIの「共通語」は依然としてRESTスタイル + JSONです。 GraphQLもgRPCもHTTPの上で動いており、URI・HTTP・表現という土台の理解(つまり本サイトの内容)は どのスタイルを選んでも必要になります。
